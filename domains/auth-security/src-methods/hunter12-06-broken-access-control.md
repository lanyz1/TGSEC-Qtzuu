# 第六技 · 越权访问 —— 系统记得你是谁，却不检查你要谁的

> 猎手视角：登录认证回答"你是谁"，访问控制回答"这个东西是不是你的"。大量系统只做了前者——你拿到自己的 ID，换一个数字，就拿到了别人的人生。

**目标读者**：具备基础 Web 测试经验的安全工程师
**前置要求**：两个测试账号（这是本技的硬要求）、HTTP 抓包改包

---

## 何时启用本技

- URL / 请求体里出现**资源标识**：`/api/users/1024/orders`、`?invoice_id=8837`、`{"docId": "f3a9..."}`
- 查看型：订单、账单、病历、工单、聊天记录、文件下载链接
- 操作型：取消订单、删除地址、修改收货信息
- 管理功能：`/admin/` 路径、角色字段（`role: "user"`）随请求提交

---

## 一、原理拆解

两类越权，两种病根：

| 类型 | 现象 | 病根 |
|------|------|------|
| **水平越权（IDOR）** | 用户 A 访问用户 B 的资源 | 服务端只"查"不"验"——按 ID 取数成功，但没比对 ID 归属 |
| **垂直越权** | 普通用户调用管理员接口 | 只在前端隐藏按钮，后端没校验角色 |

**病根的本质**：`SELECT * FROM orders WHERE id = ?` 少了半句 `AND user_id = ?`。前端的"你看不到"永远不等于后端的"你碰不到"。

---

## 二、五步猎洞法

### 第一步：识面 —— 建立"资源-标识"清单

浏览全站，登记所有带资源标识的请求，标注标识类型：数字自增（`1024`，可遍历）、UUID（不可枚举但可替换）、文件路径。同时注册 A/B 两个账号，B 当"受害陪练"。

### 第二步：定点 —— 建立归属基线

用 A 账号正常请求自己的资源，记录响应结构（字段、状态码）；用 B 账号请求 B 的资源，同样记录。基线 = "正常情况下我能看到什么"。

### 第三步：验证 —— 交叉替换

把 A 的请求里的资源标识换成 B 的（**用 B 账号的会话去取 B 的资源不需要；反过来：A 的会话取 B 的资源**）：

```http
GET /api/orders/detail?order_id=<B的订单ID>
Cookie: session=<A的会话>
```

- 返回 B 的订单数据 → 水平越权实锤
- 403/404 → 该点已做归属校验，换下一个

数字型标识顺手测遍历可行性（`order_id=10001→10002` 是否直接翻页）。

### 第四步：利用 —— 评估操作型影响

- **读**：能看谁的、什么敏感度的数据（身份证、地址、手机号）
- **写**：能否改 B 的收货地址、取消 B 的订单（操作型越权危害高一档）
- **垂直**：普通会话直接请求 `/admin/user/delete`，观察是否只是前端没显示而后端放行；或注册请求里改 `role: "admin"`（**Mass Assignment**，与越权同族）
- **批量性验证**：数字标识用脚本抽 20 个随机 ID 验证普遍性（别全量遍历，报告不需要也不体面）

### 第五步：收官 —— 量化写报告

报告公式：**影响范围 × 数据敏感度**。能遍历（ID 连续可猜）写"全量用户数据可被拖取"；UUID 不可枚举写"已知 ID 可越权访问"。附最小 PoC 请求对（A 会话 + B 资源）。

## 三、实战推演（虚构场景）

> 场景：授权测试虚构电商平台 `mall.demo-example.com`，两测试账号 A(user:1001) / B(user:1002)

1. **识面**：订单详情 `/api/order/view?orderId=`、电子发票下载 `/api/invoice?fid=`、收货地址 `/api/addr/`
2. **定点**：A 查自己订单 `orderId=50021` 正常；B 查自己的 `50035` 正常，基线建立
3. **验证**：A 的会话请求 `orderId=50035`（B 的）——返回 B 的完整订单（收货人姓名、电话、地址、商品明细），水平越权
4. **利用**：`POST /api/addr/update` 改 B 的收货地址（带 B 的 addrId）也成功——操作型越权；`/admin/user/list` 返回 403，垂直无洞
5. **收官**：抽样验证 `orderId` 在 50000-50100 区间均存在越权，报告"全量订单数据可越权读取 + 收货地址可篡改"，高危

## 四、对抗与绕过

| 防御/伪装 | 破解思路 |
|-----------|----------|
| UUID 标识"不可猜" | UUID 会从其他接口泄露（分享链接、消息推送、日志），拿到一个即可越权——**不可枚举 ≠ 访问控制** |
| 前端隐藏 admin 入口 | 直接请求接口；JS bundle 里 grep `admin`、`/api` 路径找隐藏路由 |
| 只校验了 GET，没校验 POST | 改方法重放（`GET` 换成 `POST /api/order/cancel`） |
| 归属校验放在前端逻辑 | 一切前端校验视为不存在 |
| 接口版本差异 | `/api/v1/order` 加固了，`/v2/` 上线时校验没跟上——新旧接口都要测 |
| GraphQL | 单端点查询，嵌套对象引用越权重灾区：`query { user(id:1002){ orders { items } } }` |

---

## 五、防御视角

1. **归属校验下沉到数据层**：查询条件永远带 `AND owner_id = current_user`，而非"取出后再判断"
2. 垂直：每个接口独立声明权限（默认拒绝），RBAC 中间件统一拦截，不依赖前端隐藏
3. Mass Assignment：请求字段白名单（DTO 显式声明），禁把用户提交的角色/金额字段直接绑定实体
4. 标识不可预测只能当纵深，不当防御
5. 自动化回归：CI 里加"跨账号访问必须 403"的契约测试

---

## 六、踩坑记录

- 没有第二个测试账号，是越权测试失败率第一的原因——**先想办法搞 B 账号**（哪怕找客户开一个）
- B 资源的数据在响应里与 A 的"长得一样"（都是测试数据）——先做数据标记（B 的收货人填"B测试标记"），否则看串了得出假阳性
- 遍历验证别跑全量：抽样式证明普遍性 + 停手，全量拖数在任何报告里都是减分项
- 手机 App 的 API 常比 Web 少校验——同后端多端（小程序/App/H5）**分别测**，一端加固一端裸奔是常态
- 操作型越权测试前先备份数据或用可回滚操作（"取消订单"测完别真给客户删了）

---

## 七、速查卡

```text
基线:   A查A + B查B 先记正常响应
验证:   A的会话取B的资源 = 水平越权
垂直:   普通会话打 /admin/* | 请求体改 role
批量:   数字ID抽20个证普遍性, 不全量
GraphQL: user(id:别人){...} 嵌套越权
防御:   WHERE owner_id=me | 接口级RBAC | 字段白名单
```
