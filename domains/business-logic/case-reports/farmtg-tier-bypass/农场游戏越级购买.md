# farmtg.top 渗透测试报告（阶段一）

- 日期：2026-09-04
- 目标：https://farmtg.top/（Telegram Mini App 农场游戏，bot @Joyhpyy_bot）
- 授权：用户声明为自有/授权目标；仅使用其提供的会话凭据；非破坏原则，测试账号上小幅落地
- 测试方式：静态分析前端 bundle + HTTP API + WebSocket 协议复现，绕过前端直接构造请求

## 目标结论（核心问题：能否修改后台/游戏数据）

**在已测范围内：无法通过普通玩家会话修改他人数据或管理员后台数据；游戏经济数值（金币/点券）由服务端权威计算，未发现可直接刷币的缺陷。**
存在 1 处等级门禁缺失（低危）+ 若干输入校验不规范（信息级）。资金类接口（TON 充值确认）与若干需要双号/人机验证的深度场景**未测试**（见 §5）。

## 1. 架构画像

| 层 | 技术 |
|---|---|
| 前端 | Vue3 SPA，Vercel 镜像 `farmtg-web.vercel.app`；`admin.farmtg.top` 为同一 SPA 别名 |
| 网关 | Cloudflare（反爬 + Turnstile 人机验证） |
| 后端 | Go，`farmtg.top/api/*`（未知路径返回 `404 page not found`） |
| 鉴权 | Telegram `initData` → `POST /api/auth/login`（带 fingerprint/device）→ **JWT(HS256) Bearer**，有效期 1h，内含 `tg_id / client_ip / device_id / device_verified / session_id` |
| 会话 | `server_name_session` cookie 为匿名占位，API 不认；真正鉴权走 Bearer |
| 实时 | `wss://farmtg.top/api/game/ws`：`auth` → 推送 `plots` 状态；动作 = `{type:action, rid:"<字符串>", action, data}`，回执 `{type:result, rid, ok, data/error}` |
| 人机 | `plant / harvest / harvest_all` 强制 Turnstile/gocaptcha 人机验证（`X-Human-Pass`） |
| 后台 | `/api/admin/{users,config,mails,tasks,pets,tools,levels,decorations}` —— 无独立面板，纯 JSON API |

> 关键复现细节：WS 动作的 `rid` 必须是**字符串**，数字会被服务器静默丢弃（一开始动作全部无回执即因此）。

## 2. 已确认的防护（防御面记录，均实测）

- **经济数值服务端权威**：
  - `buy_seed` 扣款由服务端按 `price×count` 计算；超大数量被拒且金币不变
  - `sell_fruits` 无果实 → `coins_gain:0`，无法凭空刷币；前端即使伪造 `count` 也以服务端返回为准
  - `upgrade_plot` 金币不足时拒绝（"金币不足，需要 300000 金币"），余额不被扣
- **任务系统服务端判完成**：领取未完成任务被拒（400）；伪任务 code 报"任务不存在"
- **种/收类强反作弊**：无 `human_pass` 时 `plant` 返回 `NEED_HUMAN_VERIFICATION` → 自动化种地收割被 Turnstile 阻断
- **后台越权边界**：玩家 token 访问 `/api/admin/*` 返回 404（资源隐藏）；匿名返回 401
- **JWT 防伪造**：`alg:none`、空密钥、弱密钥猜测均被 401 拒绝
- **transfer-seed 校验**：非法 target_key / 负数 / 超量均被 400 拦截
- **他人资料**：`GET /api/game/profile?player_key=<他人>` 仅返回公开排行数据（累计收获统计、等级、头像），无金币/库存等敏感字段

## 3. 发现

### F1【低】`buy_seed` 未强制校验作物的 `unlock_level`
- **现象**：Lv.1 测试号成功购买 Lv.13「普通小麦」（price 576）并正常入库，仅按全价扣款。
- **影响**：作物解锁等级仅是前端门槛；玩家可跳过进度提前持有高级种子。因仍需付全价金币，不直接造成通胀；若种植阶段同样未校验等级，则可低等级种高级作物（未能验证：种植被人机验证门禁挡住）。若该作物为充值/活动限定则风险上升。
- **建议**：服务端在 `buy_seed`（以及 `plant`）校验 `crop.unlock_level ≤ user.level`；把 `unlock_level` 视为服务端授权边界而非展示字段。

### F2【信息】`buy_seed` 数量参数校验不规范
- `count:-5 / 0 / 1.5` 均被静默钳制为"购买 1 个并正常扣款"，超大数返回笼统 `请求处理失败`。
- **影响**：无刷币（都正常扣款），但输入校验混乱、错误信息不明确，便于绕过类探测产生噪音。
- **建议**：显式校验 `count` 为正整数，非法值返回明确参数错误。

### F3【信息】`/api/config`、`/api/runtime-config` 无需鉴权
- 泄露完整经济参数、`plot_unlock_coins/upgrade_costs`、**TON 充值包与精确 nano-TON 价格**、运营者 TG 联系方式、前端 Vercel 地址。
- **影响**：轻微；价格等本可前端可见。建议敏感运营配置移出匿名可见范围。

### F4【信息】前端源码完整暴露协议（天然，SPA）
- 所有 API/WS 端点、动作名、payload 结构均可从公开 bundle 还原，服务端因此必须完全自校验——当前整体做到了，但任何漏网参数都易被利用（见 §5 需重点回归项）。

## 阶段二（补充）：针对运营方授权下的两个关键疑问

### Q1：普通玩家能否「修改一个作物 / 新加一个作物」？—— **不能**
证据：
- 玩家前端 bundle **不含任何 `admin` 接口引用**（`grep admin` 为空），作物目录管理入口不在玩家端
- 玩家 token 对 `/api/admin/{users,config,mails,tasks,pets,tools,levels,decorations}` 的 GET/POST/PUT **全部返回 404「资源不存在」**（角色不符时路由隐藏）；匿名访问同一路径返回 401
- 作物是**全服共享只读目录**（`GET /api/crops`）；玩家侧仅 `buy_seed`，伪造 crop_id 被拒（"种子不存在"）
- 结论：作物增改属后台/DB 管理面，玩家会话不可达；未发现从玩家 token 提权到该面的路径（JWT 伪造、alg:none、空密钥均已试，全部 401）

### Q2：TON 充值 `confirm` 能否绕过链上校验刷点券？—— **不能（未付款直接确认被拦）**
实测（最小订单 pack_6a74ac9c674377cce70cbdee，10 点券/0.1 TON，未实际付款）：

| 尝试 | HTTP | 结果 |
|---|---|---|
| 建单后**不付款**直接 `confirm{order_no}` | 400 | "请求处理失败"，点券仍 0，订单保持 `pending` |
| 重复 confirm 同一 pending 单 | 400 | 拒绝（无重复入账） |
| confirm 伪造 order_no | 400 | "订单不存在" |
| 参数污染（补 `paid/status/verified:true`） | 400 | 拒绝 |

流程：`create{pack_id}` → 返回 `pendingOrder{order_no, ton_amount, pay_to, pay_comment=FARM_<order_no>, pay_url(tonkeeper)}`；`confirm` 端侧核链上到账。
- 资金面**基础防御成立**。未做真实小额支付测试（涉及真实 TON 支出），因此"金额/备注匹配是否可被弱化"（如付 0.001 TON 冒领）**未验证**——如需彻底确认，建议运营侧用真实小额自测并核对 memo+金额校验逻辑。

## 阶段四（单号实测批：只读 + 单发，无放大，零污染）

实测账号仍 Lv.1 / exp 10 / 金币 11304 / 点券 0 / 1 地块；**健康分 100、无限制事件、enforcement 已启用**；全部探测后健康分仍 100、余额 11304，零漂移。期间共发约 30 个请求，含 2 次故意答错人机验证。

### 4.1 人机验证体系（决定自动化上限）
- **双轨**：`GET /api/game/human-verify/challenge?purpose=` 服务端按用途下发验证码——
  - `purpose=default`（种/收/偷等核心农事）→ **自建 gocaptcha**，`challenge_type=click_text`，图片 base64 内嵌返回，`expires_in=120s`
  - `purpose=friend_visit` → Cloudflare Turnstile
- `purpose` 有白名单：非法值（如 `human_verify`）返回 400 `INVALID_ARGUMENT`。服务端校验用途，非任意值可打。
- **判定模型**：`POST /api/game/human-verify {challenge_id, answer, purpose}` 错答（空/伪坐标）一律 400 `HUMAN_VERIFICATION_FAILED`「请刷新后重试」；同一 challenge_id 二次提交不回显差异（无法区分"可重试"或"已作废"），提示语要求前端刷新重取。→ **答案纯服务端校验，未见廉价绕过**；要过这关只有两条路：真解出 click_text 坐标，或走浏览器人工一次。
- 意义：`plant/harvest/harvest_all/steal-crops` 等所有**能产出收益的动作**都被 gocaptcha 挡住，自动化被压到验证码这一层；若能自动化解 gocaptcha（OCR+点选坐标），F1 的"低等级种高级作物"、收获类任务农、金币循环才可能被程序化放大。**当前未实现 solver，属运营自测建议项。**

### 4.2 校验顺序与边界（实测）
- `POST /api/game/steal-crops {target_key}`：bogus key → **先** 403 `NEED_HUMAN_VERIFICATION`，人机门在 key 校验**之前**。→ 未过验证码则无法观察更深的偷菜逻辑（好友/冷却/上限/宠物守护均未触及）。
- `POST /api/game/visit {target_key, confirm_paid_visit, expected_coin_cost}`：非法 key → 400 `target_key 非法`（key 有格式校验，非 UUID 而是 ~22 位 base64url）。付费/免费拜访的**真实结算逻辑未验证**——需一个真实好友 key（受控第二账号），且不应对真实第三方账号发起付费拜访。
- `mails` 当前为空；`POST /api/game/mails/<bogus>/claim` → 400 `无效邮件 ID`。claim IDOR 需等一封真实邮件（运营补偿/风控事件邮件）才能测。

### 4.3 玩家目录与隐私面
- `GET /api/game/all-players`：全服 **11,828 人**，按 exp 排序，`page_size` 上限 **50**（需约 237 次请求可拉全量）。每记录含 `player_key / first_name / photo_url / level / exp`；搜索接口对自账号返回空（不含自己）。
- `GET /api/game/profile?player_key=<他人>`：公开返回其 `crop_stats`（各作物累计收获量）+ 基础信息，无金币/钱包。→ 组合后 = **可枚举的 1.18 万玩家目录**（昵称+头像+等级+累计作物量），用于画像/钓鱼/骚扰/挑"肥羊"偷菜；不直接泄露资金。
- `GET /api/game/steal-leaderboard`：公开偷菜榜（含 username、steal_value、次数）——偷菜经济公开可审计。

### 4.4 任务系统与解锁链（单号为何走不通）
- 任务全量 16 项，条件 metric 为：`level / harvest_count / crop_harvest_count / unlocked_plots / weed_put_count / pest_put_count / ton_recharge_count` 等，均需收获（人机）、除草/除虫（需好友放）、升级（需 exp）、或真 TON 充值。
- `unlock_plot` 动作**不接受参数**（服务端自动解锁下一块）；实测 Lv.1 下无论带不带 index 均通用失败且不扣款——因 `levels` 表 Lv.1 `unlockable_plots=1`，已解锁 1 块 = 无下一个可解锁地。**要解锁更多必须升 Lv.2（exp 155）**，而 exp 来源（收获 / 除草除虫 +30exp）分别被人机、好友关系锁死。
- ⇒ 因此 `novice_unlock_3`（+800）、`novice_lv_3`（+300）在单号下**不可完成**，**任务领取并发双花测试在本会话无法执行**——需先有一次真实收获（浏览器过验证码）或双号除草链把账号抬到可完成任务的状态。

### 4.5 经济配置泄露要点（复核 F3）
- `plot_unlock_coins`（第 2 块 1000 起、最高 24 块 20,000,000）、`plot_unlock_exp`（逐块 10–240）、`plot_upgrade_costs=[300000, 3000000]`、`plot_yield_bonus_pct`、`register_initial_coins=12888`、`nickname_change_coin_cost=8,000,000`、**`non_friend_visit_coin_cost=1,000,000`（非好友拜访居然要 100 万金币？）**、`friend_mark_put_daily_limit=100`、`seed_transfer_daily_limit=30`、除草/除虫单次 +50 金币 +30 exp、TON 六个充值包与 nano 单价。→ 这些参数全匿名可见（阶段一 F3），为"算出最优刷法"提供精确输入（如每日除草任务 6 次 = 300 金币 + 180 exp）。

- 服务器对**所有触得到的状态改动**保持权威且闭环（定价/库存/解锁条件/人机门/健康分），单号自动化未找到可直接落地、可持续的"无中生有"路径。
- 尚未排除的高价值面全部需要额外条件：
  1. **第二受控账号**（好友关系成立）→ 偷菜结算与上限、付费拜访真实结算、放虫⇄除虫互刷循环（含每日/周任务与 exp）、friend-farm use-tool、种子转赠好友门槛与每日 30 上限、跨号"抬等级→开解锁→触发任务领取并发双花"。
  2. **一次浏览器真实收获**（过 gocaptcha）→ F1 的 plant 是否校验 unlock_level、harvest 双花/数量、任务 claim 并发。
  3. **真实小额 TON**（运营自测）→ confirm 金额/备注弱化。

## 阶段五：F1 修复工单（详细实现 + 修复方案）

### 5.1 漏洞定位与影响（修正定级）

- **入口**：WS 动作 `buy_seed`（也可推广到 `buy_pet / buy_tool`）。
- **缺陷**：服务端只校验「金币是否够」，**未校验 `user.level >= crop.unlock_level`**；解锁等级只在前端置灰/隐藏按钮。
- **影响**：低等级玩家可**按全价提前购买/持有高级种子**。本身不直接产生金币/经验；真正的伤害形态是「低等级提前种植高级作物」——该环节同样疑似未校验（被人机门挡住未实弹确认），若成立则低等级可种高收益作物，间接造成经济前移。
- **定级**：Low（单点）；若 `plant` 未校验坐实 → Medium（需运营侧用真实环境带一次人机验证复核 plant）。

### 5.2 详细复现（本次实测记录）

前置：任意已登录会话（Bearer 绑定登录 IP），金币 ≥ 单价。示例如下（普通小麦 Lv.13、price 576、crop_id `6a0dd721885b02bbd1a2c7c3`）：

1. 连接 `wss://farmtg.top/api/game/ws`，请求头带 `Origin: https://farmtg.top` + 浏览器 UA。
2. 发送鉴权帧：`{"type":"auth","token":"<Bearer>"}`。
3. 发送动作帧（**`rid` 必须是字符串**，数字会被服务器静默丢弃）：
   ```json
   {"type":"action","rid":"1","action":"buy_seed",
    "data":{"crop_id":"6a0dd721885b02bbd1a2c7c3","count":1}}
   ```
4. 实测结果（Lv.1 账号）：返回 `ok`，金币 −576，库存「普通小麦 ×1」。服务端只扣了钱，没有校验 Lv.1 < Lv.13。
5. 附带（F2）：`count=-5 / 0 / 1.5` 被静默钳为「买 1」，超大量返回笼统 `请求处理失败`，说明 `count` 无显式白名单校验。

> 用户等级服务端可信（WS `plots.user.level`），作物定义也在服务端目录（`GET /api/crops`），因此等级校验完全可以在服务端完成，不依赖任何客户端输入。

### 5.3 根因

`unlock_level` 被当作**纯展示字段**：授权判断（能否购买/能否种）放到了前端按钮层，后端 `buy_seed` handler 只执行 `coins >= price*count` 就放行。SPA bundle 公开，任何人可绕过 UI 直接构造动作帧。

### 5.4 修复方案（Go 伪码，防御纵深）

核心原则：**所有授权判断放服务端，且购买与发放在同一事务/同一把锁内**；人机验证（gocaptcha/Turnstile）只当反自动化层，**不得充当授权层**。

**(1) `buy_seed` 服务端校验（主修复）**

```go
type buySeedReq struct {
    CropID string `json:"crop_id"`
    Count  int    `json:"count"`
}

const maxBuyPerReq = 1000

func (s *Svc) BuySeed(ctx, user *User, req buySeedReq) (*Result, error) {
    if req.Count <= 0 || req.Count > maxBuyPerReq {          // 修 F2
        return nil, ErrParam("INVALID_COUNT", "count 必须为 1..%d 的整数", maxBuyPerReq)
    }
    crop, err := s.crops.ByID(ctx, req.CropID)               // 作物只从服务端目录取
    if err != nil { return nil, ErrNotFound("资源不存在") }    // 别把"是否锁死/停售"当404

    return s.db.Tx(ctx, func(tx *Tx) error {
        u, err := tx.LockUser(ctx, user.ID)                  // SELECT … FOR UPDATE（防并发双花）
        if err != nil { return err }
        if u.Level < crop.UnlockLevel {                      // ★ 核心：等级门禁
            return Err("LEVEL_NOT_ENOUGH", "需要 Lv.%d 才能购买该种子", crop.UnlockLevel)
        }
        total := crop.Price * req.Count                      // 用 int64 计算，注意溢出
        if u.Coins < total { return Err("COINS_NOT_ENOUGH", "金币不足") }
        if err := tx.DeductCoins(ctx, u.ID, total); err != nil { return err }
        if err := tx.AddSeeds(ctx, u.ID, crop.ID, req.Count); err != nil { return err }
        return nil                                           // 同事务，扣款+入库存原子
    })
}
```

**(2) `plant` 同样必须校验（真正的伤害点）**——种子允许"低等级持有、升级后播种"，但播种瞬间以**当前等级**为准：

```go
func (s *Svc) Plant(ctx, user *User, plotIdx int, cropID string) (*Result, error) {
    crop, err := s.crops.ByID(ctx, cropID); if err != nil { return nil, ErrNotFound("资源不存在") }
    u, err := s.db.LockUser(ctx, user.ID)
    if err != nil { return nil, err }
    if u.Level < crop.UnlockLevel {                          // ★ plant 时间样卡等级
        return nil, Err("LEVEL_NOT_ENOUGH", "需要 Lv.%d 才能种植", crop.UnlockLevel)
    }
    // 校验该地块未占用、有对应种子、在可种植范围
    // planted_at / mature_at 一律服务端生成，不接受客户端时间戳
    ...
}
```

**(3) `transfer_seed` 不需按等级拦**（好友送高级种子是设计功能），封堵落在播种方（plant 的收货人等级校验）。若要更严，可在 transfer 时附加提醒，但**不要**禁转。

**(4) 同类入口一次排查**：`buy_pet / buy_tool` 加同样断言；新增**统一辅助函数**避免遗漏：

```go
func authorizeCropLevel(u *User, lv int) error {
    if u.Level < lv { return Err("LEVEL_NOT_ENOUGH", "需要 Lv.%d", lv) }
    return nil
}
```

**(5) 幂等/并发**：动作加 `rid`/nonce 去重（服务端对已处理的 rid 直接返回原结果），防止同一动作帧重放造成双扣双发；即便无 rid，事务内 `FOR UPDATE` 也挡住余额竞态。

**(6) 错误码契约**：等级不足返回 `400 LEVEL_NOT_ENOUGH`（带 `need_level`），前端据 `need_level` 展示；参数错误返回 `INVALID_COUNT`。别再用笼统 `请求处理失败`。

**(7) 监控兜底**：若出现 `user.level < crop.unlock_level` 却购买/种植成功，说明有别的入口或 DB 异常 → 记为风控事件并告警（对接现有 risk-score 体系）。
