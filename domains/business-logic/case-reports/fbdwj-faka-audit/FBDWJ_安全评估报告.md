## 1. 执行摘要

站点为典型「发卡站」架构：前台下单/查单 + `/admin` 管理后台。评估过程中确认多处**严重鉴权缺失**，可导致：

1. **订单与卡密（secret）批量泄露**（前台查单接口未授权）  
2. **后台写操作未授权**（配置/分类/订单模块的 del、edit 类接口在无登录态下仍返回业务 JSON）  
3. **订单字段可被未授权篡改**（含 `secret` 等字段，已用无害标记验证读写闭环）  
4. 后台存在可枚举的管理员用户名（如 `admin` / `Admin` 返回「密码错误」类差异），存在口令攻击面（本轮常见弱口令未命中，**未取得后台会话**）

公开查单并集可见：**含 secret 的订单约 165 条**；订单记录并集约 **173** 条；id 约在 **5–241**，区间内约 **64** 个 id 在公开并集中缺失（不代表库内一定不存在，仅表示当前未授权可见面未覆盖）。有密订单金额合计约 **¥10,467**（统计口径：有 secret 的订单 `amount` 求和）。

**综合风险等级：严重（Critical）。**  
建议立即下线或 WAF 封禁相关接口，轮换全部已泄露卡密/查询密码，并做全库订单完整性校验。

## 3. 漏洞详情

### 3.1 【严重】前台订单/卡密未授权查询 — `POST /cxdd`

| 项 | 说明 |
|----|------|
| 类型 | Broken Access Control / 敏感数据过度暴露 |
| 位置 | `POST https://www.fbdwj.com/cxdd`，参数如 `so` |
| 现象 | 未登录情况下，宽泛或猜测性 `so` 可返回订单数组；元素中含 **secret、password、contact、create_ip** 等 |
| 影响 | 卡密与查单密码批量泄露；买家隐私（联系方式/IP）泄露；可支撑二次撞库与社工 |
| 可见规模（本轮并集） | 有 secret **≈165**；订单行 **≈173**；单次宽查询存在服务端 **条数上限**（约百余级，非无限 dump） |
| 补充 | 精确 `trade_no` 可命中单笔；模糊/前缀策略受服务端匹配与 LIMIT 约束 |
| CVSS 概念映射 | 机密性高、完整性低、可达性网络、无需权限 → **Critical** |

**修复建议（优先）：**

1. 查单必须绑定强因子：订单号 + 下单时下发的**高熵查询码** + 可选邮箱/手机 OTP；禁止仅靠短 `so` 或弱 password。  
2. `secret` **禁止**出现在「列表/模糊搜索」响应中；仅在通过强校验后的「单笔详情」返回一次，并审计。  
3. 对 `/cxdd` 做登录态或 signed token、速率限制、异常 `so` 模式告警。  
4. 已泄露卡密视为失陷：**全部作废/重置**，通知受影响买家。  
5. 日志审计：按 IP 统计 `/cxdd` 频率与命中率。

---

### 3.2 【严重】后台订单写接口未授权 — `/admin/dingdan/edit_ajax` 等

| 项 | 说明 |
|----|------|
| 类型 | 未授权管理功能 / IDOR 写 |
| 位置 | 如 `POST /admin/dingdan/edit_ajax`（以及同模块 `del` 等） |
| 现象 | **无有效管理员会话**时，带 `id` 等参数仍返回 `state=1`「修改成功」类 JSON |
| 已验证影响 | 可改写订单字段；对 `secret` 写入测试标记后，前台查单可读回，形成**读写闭环** |
| 关联 | `/admin/dingdan/del` 类接口亦出现「删除成功」类未授权响应（需业务侧确认是否空跑/真删） |
| 影响 | 篡改发货状态、卡密、金额关联字段；破坏订单完整性；配合前台查单可扩大数据面 |

**修复建议：**

1. 所有 `/admin/**` 写接口统一 **Session/JWT 鉴权 + 角色校验**；未登录一律 401/登录页，禁止业务 JSON。  
2. 写操作 CSRF Token；关键字段（secret、amount、status）二次鉴权与操作日志。  
3. 全量审计 `edit_ajax` / `set_ajax` / `del` 在未登录下的响应，做回归测试。  
4. 对历史订单做完整性校验（secret 是否被异常改写）。

---

### 3.3 【高危】后台其它模块未授权写 — peizhi / fenlei 等

| 项 | 说明 |
|----|------|
| 位置 | 如 `/admin/peizhi/del`、`/admin/fenlei/del`、部分 `*_ajax` |
| 现象 | 未登录返回「删除成功」或业务 JSON 结构（`state`/`message`） |
| 影响 | 配置/分类被篡改或删除 → 业务中断、挂马页面、支付回调配置被改等（视真实 DB 写入而定） |
| 栈/包名线索 | 500 响应曾暴露 `maihao.com.Web.ArticleWeb.showList` 等，利于攻击者映射控制器 |

**修复建议：** 与 3.2 相同的全局 Admin 拦截器；生产关闭详细异常栈；统一错误页。

---

### 3.4 【中高】后台认证面：用户名枚举 + 验证码可自动化

| 项 | 说明 |
|----|------|
| 位置 | `/admin/handlogin`、`/admin/code`、`/admin/checkCode` |
| 现象 | `admin` / `Admin` 等返回「密码错误」；不存在用户名可能不同文案（枚举） |
| 验证码 | 图形验证码可被 OCR 类方案尝试（成功率依赖实现强度） |
| 本轮结果 | 常见弱口令与部分字典**未命中**；**未获取后台登录会话** |
| 影响 | 一旦弱口令或验证码形同虚设，将直接拿到完整卡密库与配置 |

**修复建议：**

1. 统一登录失败文案；账户锁定 / 渐进延迟 / IP 与账号双维度限速。  
2. 验证码改为行为验证或二次 OTP；禁止可预测/简单字符集。  
3. 管理员强口令 + 强制 2FA；后台限制来源 IP。  
4. 登录与验证码校验接口防刷。

|----|------|

## 7. 检测与验证建议（防御方）

以下用于**自有环境回归**，不提供攻击载荷：

1. **未登录**请求任意 `/admin/**/edit_ajax|del|set_ajax`，期望：302 登录页或 401，且 body **无** `state/message` 业务成功结构。  
2. **未登录**请求查单接口，期望：无 secret；模糊搜索无列表或仅有脱敏占位。  
3. 登录后改密/发货，审计表应有操作者、IP、前后差量。  
4. 对 `/cxdd` 做限流单测与压测告警阈值。  
5. 备份与导出接口必须鉴权 + 下载审计。

## 9. 结论

`www.fbdwj.com` 当前最致命问题不是「弱口令进了后台」，而是：

1. **前台查单把卡密当查询结果字段吐出**；  
2. **后台写接口在未登录时仍可改订单（含 secret）**。  

二者叠加后，机密性与完整性同时破产。修复必须以**鉴权与最小暴露**为中心，并假定历史卡密已泄露而做全量轮换。
