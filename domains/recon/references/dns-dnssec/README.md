# DNS 解析安全与 DNSSEC

> 公开资料学习包；资料核对日期：2026-07-20。只包含原创中文摘要、来源链接和无破坏性的观察练习，不保存第三方原文、真实凭据或目标数据。

## 本方向解决什么问题

DNS 安全不是一个开关，而是四类控制的组合：

1. **数据来源与完整性**：DNSSEC 让验证器确认已签名 DNS 数据来自预期的签名链，且签名后未被修改。
2. **传输机密性与对端认证**：DoT、DoH、DoQ 保护部署它们的传输段，不能替代 DNSSEC 的数据来源验证。
3. **控制面安全**：注册商、DNS 托管平台、签名系统和密钥管理仍需 MFA、最小权限、变更审计和恢复流程。
4. **可用性与检测**：冗余权威服务、验证器监控、签名/委派巡检、保护性 DNS 和日志共同处理故障、滥用与事件响应。

## 结论先行

- DNSSEC 提供的是**已签名 RRset 的来源认证和完整性**，不提供查询机密性，也不保证业务端点本身可信。
- DoT、DoH、DoQ 提供**传输保护**；递归解析器仍能看到完整查询，权威侧可见范围还受缓存与 QNAME 最小化影响。
- DNSSEC 与加密 DNS 不是替代关系：前者回答“数据能否由信任链验证”，后者回答“这一段传输是否被加密并认证对端”。
- 源端口/事务 ID 随机化和 DNS Cookies 能提高伪造应答难度，但 DNS Cookies 只对离路径攻击者提供有限保护，不能抵御路径上攻击者。
- DNSSEC 验证有 `Secure`、`Insecure`、`Bogus`、`Indeterminate` 四种语义状态；“未签名”不等于“签名错误”，不能把它们统一当成安全或统一当成攻击。
- 注册商账号若被接管，攻击者可能修改 NS、DS 或解析记录；DNSSEC 不能替代注册商 MFA、变更审批和域名资产审计。
- 密钥轮换、签名过期、父子 DS 不一致、时间错误都可能把正确业务变成 `Bogus`，所以 DNSSEC 是持续运营能力，不是一次性配置。

## 最小心智模型

### 角色

- **Stub resolver**：应用或操作系统发起查询的一端，常把验证委托给递归解析器。
- **Recursive resolver**：迭代查询、缓存结果并可执行 DNSSEC 验证。
- **Authoritative server**：为所辖 zone 提供权威数据；签名通常发生在权威数据发布链路中。
- **Registrar / Registry / Parent zone**：承载域名控制面和父区委派；父区中的 DS 将子区接入 DNSSEC 信任链。

### 信任链

典型验证路径为：

`本地信任锚 → 父区 DNSKEY/RRSIG → 父区 DS → 子区 DNSKEY/RRSIG → 目标 RRset`

核心记录：

- `DNSKEY`：区的公开验证密钥。
- `DS`：父区对某个子区 DNSKEY 的摘要引用。
- `RRSIG`：对 RRset 的签名。
- `NSEC` / `NSEC3`：对“不存在”给出可验证证明。

信任链完整且签名有效才是 `Secure`。存在安全委派但签名缺失、过期、算法不受支持或数据不一致时是 `Bogus`，通常表现为验证解析器返回失败，而不是静默降级到未验证数据。

## 威胁与控制边界

### 离路径伪造和缓存投毒

- 基线：不可预测事务 ID、尽可能大的随机源端口空间、严格匹配查询与应答。
- 增强：DNS Cookies 对离路径伪造提供有限保护。
- 根因控制：对已签名区执行 DNSSEC 验证。
- 边界：NAT 端口改写会削弱源端口随机化；DNS Cookies 不抵御路径上观察者。

### 路径上窃听或篡改

- DoT、DoH、DoQ 可保护启用它们的传输段。
- DNSSEC 可发现已签名数据在签名后被篡改，但不隐藏查询内容。
- 如果终端只信任上游递归解析器的 AD 位，终端到解析器之间也必须是受信或认证的通道；否则应在终端自行验证。

### 域名控制面被接管

- 对注册商、注册局、DNS 托管和签名平台实施强 MFA、独立恢复渠道、最小权限和变更告警。
- 定期核对 NS、DS、A/AAAA、MX、CAA 等关键记录，并监控证书透明度日志。
- DNSSEC 私钥或可修改 DS 的控制面被攻破后，攻击者可能发布“密码学上有效但恶意”的数据。

### 隐私泄露

- QNAME 最小化减少递归解析器向上游权威服务器披露的名称部分。
- 它不能向递归解析器隐藏完整查询，也不是线路加密。
- 加密 DNS 会改变传统网络监测的可见性；企业应把策略、日志和检测放在获准的解析器处，而不是依赖旁路明文抓包。

### 可用性与运营故障

- 分离面向互联网的权威服务与递归服务，避免公开递归和不必要的攻击面。
- 监控 RRSIG 过期窗口、DS/DNSKEY 一致性、验证失败率、时钟、信任锚状态和轮换阶段。
- 自动化不等于盲目变更：父区消费 CDS/CDNSKEY 时应校验所有权威服务器的一致性；不一致时中止。

## 2026 年时效提醒

- NIST SP 800-81r3 于 2026-03-19 发布并取代 SP 800-81-2；其发布页在 2026-07-10 标注了潜在勘误，实施前需查看最新勘误。
- RFC 9904 已在 2025-11 取代 RFC 8624，并把 DNSSEC 算法要求的权威状态移到 IANA 注册表。因此不要照抄旧文档中的静态算法表。
- 截至 2026-07-20，IANA 计划在 **2026-10-11** 让 KSK-2024（key tag `38696`）开始签署根区，取代当前签名的 KSK-2017。验证器应按厂商流程更新信任锚并监控自动轮换，不应手工抄写本页参数作为配置。
- RFC 9718 已取代 RFC 7958；根信任锚的规范入口是 IANA 发布的 XML 集合。
- RFC 9975（2026-05）补充了 CDS/CDNSKEY 与 CSYNC 的跨权威服务器一致性要求。
