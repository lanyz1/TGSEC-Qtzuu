# 定义

OAuth 2.0 授权码流的安全本质，是把一次浏览器发起的授权交易绑定到正确的客户端实例、用户代理、授权服务器和资源服务器，并限制任何泄露的授权码或令牌被另一方重放。

OpenID Connect（OIDC）在 OAuth 2.0 上增加身份层。OAuth 访问令牌表达的是“可以访问什么”，OIDC ID Token 表达的是“授权服务器认证了谁”。不能仅凭一个普通 OAuth 访问令牌把用户登录身份建立起来。

# 学习目标

完成本卡片后应能：

1. 解释 Authorization Code、Access Token、Refresh Token、ID Token 的边界。
2. 说明 PKCE、`state`、OIDC `nonce` 分别绑定什么，不能用一个参数机械替代全部控制。
3. 审查重定向 URI、授权服务器发行者、令牌 audience 与刷新令牌轮换。
4. 区分 PKCE 与 DPoP/mTLS：前者保护授权码交易，后者降低令牌泄露后的重放价值。
5. 为客户端、授权服务器和资源服务器设计低影响回归检查。

# 边界

## 属于本技术的情况

- OAuth 2.0 Authorization Code Flow 与 PKCE。
- OIDC Authorization Code Flow 中 ID Token 的基本校验边界。
- 授权响应 CSRF、授权码注入、Mix-Up、令牌重放和刷新令牌重放。
- 重定向 URI、授权服务器元数据、issuer、audience、scope、DPoP、mTLS 和 PAR。

## 不属于本技术的情况

- 用户名密码认证器本身、MFA 强度和账号找回。
- JWT 通用算法安全、密钥轮换和 JWKS 缓存的完整专题。
- 应用自身的对象级授权；访问令牌有效不代表对任意对象都有权限。
- SAML、Kerberos 或浏览器 Cookie 会话的完整设计。

## 容易混淆的相邻概念

- OAuth 是授权框架，不是单独的登录协议；OIDC 才定义标准身份层。
- PKCE 不是授权码加密，也不是客户端认证。它证明兑换方掌握本次交易的 `code_verifier`。
- `state` 主要绑定浏览器交易并防 CSRF；OIDC `nonce` 绑定客户端会话与 ID Token并防重放；两者语义不同。
- DPoP 不是 TLS 的替代品，也不能阻止已在客户端执行上下文中的恶意脚本借用签名能力。

# 成因模型

- 信任边界：浏览器前通道、客户端后端、授权服务器、令牌端点、资源服务器。
- 可控输入：`redirect_uri`、`state`、`code`、`iss`、`code_challenge`、`code_verifier`、令牌和资源地址。
- 高价值资产：授权码、访问令牌、刷新令牌、ID Token、客户端密钥和 DPoP 私钥。
- 危险操作：把授权码发给错误令牌端点、接受错误发行者、向错误资源服务器发送令牌、重复兑换或刷新。
- 缺失控制：交易绑定、精确 URI 匹配、发行者校验、audience 校验、最小权限、重放检测和安全日志。

# 安全模型

## 1. 默认选择 Authorization Code Flow

当前安全基线是使用 `response_type=code`，让访问令牌从后通道的令牌端点返回。RFC 9700 §2.1.2 规定客户端不应使用把访问令牌直接放入授权响应的 Implicit Grant，除非能同时解决令牌注入、泄露和重放问题。

Resource Owner Password Credentials Grant 不得使用。它把用户凭据暴露给客户端，扩大泄露面，也难以适配多步骤认证和 WebAuthn。

## 2. 用 PKCE 把授权码绑定到本次交易

客户端为每次授权请求生成新的高熵 `code_verifier`，并发送：

`code_challenge = BASE64URL(SHA256(ASCII(code_verifier)))`

关键约束：

- `code_verifier` 长度为 43 至 128 个未保留字符。
- RFC 7636 建议至少 256 bit 熵，可由密码学安全随机源生成 32 字节再做 Base64url 编码。
- 新实现使用 `S256`，不降级到 `plain`。
- 授权服务器把 challenge、method 及“本次是否启用 PKCE”绑定到授权码。
- 令牌端点只有在 verifier 与原 challenge 匹配时才继续处理，否则返回 `invalid_grant`。
- 若授权请求没有 challenge，后续却出现 verifier，授权服务器必须拒绝，避免 PKCE 降级。
- 公共客户端必须使用 PKCE；机密客户端也推荐使用。客户端密钥不能替代交易级绑定。

PKCE 的停止边界：它让截获的授权码在缺少 verifier 时无法兑换，但不保护已经泄露的访问令牌和刷新令牌。

## 3. 分清 `state`、PKCE 与 OIDC `nonce`

- `state`：一次性、不可预测，并与发起交易的用户代理会话绑定。若其中携带业务状态，还要防篡改和调包。
- PKCE：把授权请求与令牌请求绑定，可防授权码截获、注入，并在确认授权服务器支持时提供强 CSRF 防护。
- OIDC `nonce`：把客户端会话与 ID Token 绑定。发出 nonce 后，客户端必须校验 ID Token 中返回的值，并在校验成功前不得使用任何本次令牌。

仅当客户端已经可靠确认授权服务器支持并正确强制 PKCE 时，才可依赖 PKCE 的 CSRF 防护；否则仍需 `state` 或 OIDC `nonce`。业务系统常同时保留 `state` 与 PKCE，以分离交易状态和授权码绑定职责。

## 4. 精确限制重定向

- 授权服务器基线是对预注册 `redirect_uri` 做精确字符串匹配；原生应用 localhost 回调的动态端口是规范例外。经客户端认证且完整性受保护的 PAR/JAR 请求可按规范和本地策略建立每请求 URI，但仍要验证并绑定目标，不能退化成任意跳转。
- 授权响应只通过加密连接返回；原生应用 loopback 回调是 HTTP 例外。
- 客户端和授权服务器不得提供把查询参数直接转发到任意地址的开放重定向。
- 令牌端点验证授权码绑定的客户端、实际重定向 URI、PKCE 信息和单次使用状态。
- 处理可能仍含用户凭据的 POST 后，不使用 HTTP 307 跳转到客户端；RFC 9700 建议需要 HTTP 跳转时使用会明确转换为 GET 的 303。

## 5. 多授权服务器场景绑定发行者

只连接一个授权服务器的客户端没有 Mix-Up 前提；一旦支持两个或更多授权服务器，就必须把每次交易绑定到预期 issuer。

优先做法：

1. 发起授权时记录预期 issuer，并与用户代理交易绑定。
2. 接收授权响应时读取 RFC 9207 `iss`，用简单字符串比较与预期 issuer 对照。
3. 不匹配、缺失但配置声明支持，或出现互相冲突的多个 issuer 时立即终止。
4. 仅存一个授权端点 URL 不够；issuer 对应的授权端点、令牌端点和元数据必须作为一组信任配置。

## 6. 限制访问令牌的使用范围

资源服务器不能只验证签名或“令牌看起来有效”，还要验证：

- `aud` 是否包含当前资源服务器。
- scope、细粒度授权详情和实际动作是否匹配。
- issuer、有效期、令牌状态及部署要求的其他声明。
- 对象级权限是否在业务层再次成立。

授权服务器应只签发完成当前用途所需的 audience、资源和动作。Audience 限制减少令牌被错误资源服务器收集后转用的范围，scope 限制令牌在正确资源服务器内能做的动作；两者不等价。

## 7. 降低访问令牌重放价值

Bearer Token 的持有者即可使用它。高价值场景可采用发送者约束：

- DPoP：客户端用私钥为请求生成证明，服务端校验签名、`jti`、`htm`、`htu`、`iat`、可选 nonce，以及资源请求中的 `ath`，并核对令牌绑定的公钥。
- mTLS：把令牌绑定到客户端证书，由授权服务器和资源服务器核对证书指纹。

DPoP 仍必须配合 HTTPS。若攻击者同时取得令牌和私钥，或能在浏览器应用上下文中调用签名能力，发送者约束会被削弱；因此仍需防 XSS、保护密钥和限制令牌寿命。

## 8. 检测刷新令牌重放

公共客户端的刷新令牌必须采用以下至少一种机制：

- 发送者约束，例如 DPoP 或 mTLS。
- 刷新令牌轮换：每次刷新签发新令牌并使旧令牌失效，同时保留同一授权链关系。旧令牌再次出现时撤销当前活跃链并要求重新授权。

刷新令牌还应绑定原同意的 scope 与资源服务器，在长期不活动后过期，并可在密码变更、授权撤销等安全事件后撤销。

轮换主要提供“重用检测与止损”，不表示刷新令牌从未泄露，也不能可靠判断攻击者和合法客户端谁先提交。

## 9. 高保证场景可使用 PAR

Pushed Authorization Requests（PAR）让客户端通过与授权服务器的直接 HTTPS 请求先提交授权参数，再把短期、客户端绑定、原则上单次使用的 `request_uri` 放入浏览器流程。

PAR 可减少授权参数经浏览器、日志和 Referer 暴露，并把客户端认证与部分请求校验前移。它不替代 PKCE 或 `state` / `nonce`，也不消除重定向目标的验证与交易绑定。经认证 PAR 可按 RFC 9126 §2.4 由策略建立每请求 redirect URI，但授权端点仍需验证 pushed request 及 `request_uri` 的生命周期和客户端绑定。

## 10. 原生应用使用外部用户代理

原生应用通过系统浏览器等外部用户代理发起授权，公共原生客户端必须使用 PKCE。分发在安装包中的共享 `client_secret` 不能视为机密凭据。

# OIDC ID Token 最小校验边界

OIDC 客户端在建立登录会话前至少确认：

1. 签名与算法符合客户端注册和发行者配置。
2. `iss` 精确等于预期发行者。
3. `aud` 包含本客户端 ID；多 audience 时按规范处理 `azp`。
4. `exp` 尚未过期，`iat` 等时间声明符合本地策略。
5. 发出过 `nonce` 时，返回值必须与本次交易保存值一致且只能使用一次。
6. 从 UserInfo 获取数据时，其 `sub` 必须精确等于 ID Token 的 `sub`。

Access Token 不能替代 ID Token 用来证明用户已登录；ID Token 也不应作为普通 API Bearer Token 使用。

# 安全验证

只在隔离环境、自有系统或明确授权范围执行。每项达到预期拒绝证据后停止，不尝试访问他人资源。

1. 注册 URI 的 scheme、host、path、query 任一非允许差异应被拒绝，不能用前缀、后缀或通配匹配放行。
2. 同一授权请求中，用错误 verifier 兑换应返回 `invalid_grant`。
3. 同一授权码第二次兑换应失败。
4. 授权请求没有 challenge、令牌请求却带 verifier 时应被拒绝。
5. `state` 或 OIDC `nonce` 不匹配、已使用、过期时应终止流程，且不得先建立会话。
6. 多发行者客户端收到错误 `iss` 时应终止，授权码不得发往任何令牌端点。
7. 资源服务器收到错误 audience 或超出 scope 的令牌时应拒绝。
8. 刷新令牌轮换后重放旧值，应触发令牌链撤销或等价的风险处置。
9. DPoP proof 的签名、HTTP method、URI、时间窗、`jti`、`ath` 或密钥绑定任一不符时应拒绝。
10. PAR 的 `request_uri` 过期、跨客户端使用或非预期重复使用时应拒绝。
11. 原生应用不能以内嵌 WebView 代替规范要求的外部用户代理。
12. 登录后的本地会话只能在全部协议校验成功后创建或升级权限。

# 检测与排查

## 代码审计线索

- `redirect_uri` 使用 contains、startsWith、正则通配或仅比较域名。
- 客户端生成固定或低熵 `state`、`nonce`、verifier，或在多个并发登录间共用。
- 授权回调收到错误参数后仍继续兑换 code。
- 令牌端点只在“有 challenge 时”校验 PKCE，却不记录本次授权是否原本要求 PKCE。
- 多发行者客户端由回调参数直接选择 token endpoint。
- 资源服务器只验 JWT 签名，不验 issuer、audience、scope 和业务对象权限。
- 刷新令牌轮换后不保存令牌族关系，无法对重用做链级撤销。
- DPoP 只验签名，不验 `htm`、`htu`、时间窗、`jti`、`ath` 或公钥绑定。
- 把 Access Token 当登录凭据，或把 ID Token 直接发给业务 API。

## 日志与遥测

建议记录交易 ID 的不可逆摘要、客户端 ID、发行者、失败阶段、错误类别、重放判定和策略版本；不得记录完整 code、token、verifier、nonce、客户端密钥或 DPoP 私钥。

高价值告警信号：

- 同一授权码或刷新令牌摘要重复使用。
- redirect URI、issuer、audience、PKCE method 或 DPoP 校验异常突增。
- 同一授权链在短时间内来自不兼容的客户端实例或密钥。
- token endpoint 出现“有 verifier 但原交易无 challenge”。
- 资源服务器收到大量 wrong-audience 令牌。

## 常见误报

- 用户刷新回调页造成重复 code 兑换；仍应拒绝第二次兑换，但可按相同交易 ID 降噪。
- 移动端 loopback 回调端口变化属于 RFC 8252 明确例外，不应误报成任意 redirect URI。
- 代理层重写外部 scheme 或 host 会造成 issuer/redirect 判断异常，应修正可信代理边界，而不是放宽匹配。

# 修复与回归

## 根因修复

- 把交易状态集中保存为一次性记录：预期 issuer、客户端、redirect URI、state、nonce、PKCE challenge、创建时间和消费状态。
- 采用维护良好的 OAuth/OIDC 库，并锁定允许的 flow、issuer、算法、redirect URI 与资源 audience。
- 让授权服务器和资源服务器负责关键安全判定，避免把全部信任放在客户端自律上。
- 对访问令牌和刷新令牌分别建立泄露后控制：短寿命、最小权限、audience、发送者约束、轮换和撤销。

## 纵深防御

- 发布并消费授权服务器元数据，减少端点和能力误配置。
- 高风险客户端采用 PAR、DPoP 或 mTLS。
- 浏览器客户端继续防 XSS；原生应用使用平台密钥存储并限制回调劫持。
- 对 token、code、verifier 和身份声明实施日志脱敏与数据最小化。

## 不完整修复反例

- 只增加 `state`，却不校验 redirect URI、issuer 或 PKCE。
- 有客户端密钥就关闭 PKCE。
- 把 `plain` 政名后继续传输原 verifier。
- 轮换刷新令牌但不追踪令牌族，旧值重放时只返回错误而不止损。
- 部署 DPoP 后取消 HTTPS、audience 或 XSS 防护。
- PAR 接口校验过一次后，浏览器阶段完全不验证 `request_uri` 生命周期与绑定。

# 标准映射

- RFC 9700：当前 OAuth 2.0 安全最佳实践。
- RFC 7636：PKCE。
- RFC 8252：原生应用 OAuth。
- RFC 9207：授权响应 issuer 标识与 Mix-Up 防护。
- RFC 9449：DPoP。
- RFC 9126：PAR。
- OpenID Connect Core 1.0 Errata Set 2：身份层与 ID Token。
- CWE-352：跨站请求伪造，可覆盖部分授权回调交易绑定缺失。
- CWE-601：开放重定向。
- 本主题跨多个信任边界，不应强行映射成单一 CWE、CAPEC 或 MITRE ATT&CK 技术。
