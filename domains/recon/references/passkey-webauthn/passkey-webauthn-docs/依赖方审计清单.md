# 使用方法

按“服务端证据 → 失败路径 → 状态是否变化”的顺序核对。浏览器弹窗、前端成功回调、设备名称和产品文案都不是服务端认证证据。

结论分为：

- **阻断项**：缺失后可直接造成认证绕过、跨账号绑定或可重放，应在上线前修复。
- **策略项**：取决于业务保证级别，但必须有明确决策和测试。
- **风险信号**：不能单独定性漏洞，应进入风险评分、告警或加强验证。

# 一、依赖方配置

- [ ] **阻断项**：RP ID 来自服务端固定配置，不接受请求参数、Host 或未受信代理头覆盖。
- [ ] **阻断项**：允许 origin 使用完整精确值，生产、预发布和开发环境相互隔离。
- [ ] **阻断项**：服务端只接受自己支持的 COSE 算法，算法策略不由客户端决定。
- [ ] **策略项**：`userVerification` 的配置与业务声称的单因素/多因素保证一致。
- [ ] **策略项**：attestation 为 `none` 或明确的企业准入策略，不存在“请求了但不验证”。
- [ ] **策略项**：同步型与设备绑定型凭据的准入和敏感操作策略有文档依据。

# 二、challenge 与交易状态

- [ ] **阻断项**：challenge 由服务端密码学随机源生成，至少 16 字节。
- [ ] **阻断项**：challenge 绑定 ceremony 类型、账号或登录上下文、签发时间和过期时间。
- [ ] **阻断项**：返回 challenge 与服务端保存值精确比较。
- [ ] **阻断项**：过期、错配、跨会话和已消费 challenge 均失败。
- [ ] **阻断项**：多实例和并发请求下只有一个结果能原子消费 challenge。
- [ ] **阻断项**：注册 challenge 不能用于认证，认证 challenge 不能用于注册。

# 三、注册验证

- [ ] **阻断项**：`clientDataJSON.type == "webauthn.create"`。
- [ ] **阻断项**：challenge、origin 和 `rpIdHash` 全部验证。
- [ ] **阻断项**：UP 已设置；策略要求 UV 时，UV 也已设置。
- [ ] **阻断项**：凭据公钥算法属于本次允许集合。
- [ ] **阻断项**：attestation object、authenticator data 和扩展按库与策略验证。
- [ ] **阻断项**：credential ID 不能绑定到其他账号，数据库存在唯一约束。
- [ ] **阻断项**：所有验证完成后才保存公钥并消费 challenge。
- [ ] **策略项**：`user.id` 是不含邮箱、用户名等 PII 的稳定内部 user handle。
- [ ] **策略项**：按实际用途保存 transports、AAGUID、UV、BE/BS 等最小元数据。

# 四、认证验证

- [ ] **阻断项**：credential ID 存在，且绑定到本次被认证账号。
- [ ] **阻断项**：用户名无关流程要求 `userHandle`，并验证其与 credential ID 指向同一账号。
- [ ] **阻断项**：`clientDataJSON.type == "webauthn.get"`。
- [ ] **阻断项**：challenge、origin 和 `rpIdHash` 全部验证。
- [ ] **阻断项**：UP 已设置；策略要求 UV 时，UV 也已设置。
- [ ] **阻断项**：使用该 credential ID 的已存公钥验证 assertion 签名。
- [ ] **阻断项**：扩展输出不能改变未授权的账号、origin、RP ID 或保证级别。
- [ ] **阻断项**：全部验证完成后才消费 challenge、轮换会话并标记认证强度。
- [ ] **风险信号**：非零 `signCount` 不递增时产生事件；不把单项异常冒充克隆实锤。
- [ ] **策略项**：始终为零的计数器按兼容策略处理，不错误拒绝所有此类认证器。

# 五、凭据生命周期

- [ ] **阻断项**：新增 passkey 需要与目标保证级别匹配的再认证，不只检查现有 Cookie。
- [ ] **阻断项**：删除、替换和恢复接口执行 CSRF 防护、服务端授权和再认证。
- [ ] **阻断项**：不能把同一 credential ID 并发绑定到多个账号。
- [ ] **阻断项**：失窃、妥协或用户请求后能立即撤销具体 credential ID。
- [ ] **策略项**：鼓励至少两种独立认证手段，避免单设备丢失后被迫弱恢复。
- [ ] **策略项**：删除最后一个强认证器有额外确认和后备路径检查。
- [ ] **策略项**：新增、删除、恢复和撤销均通过独立渠道通知用户。
- [ ] **策略项**：用户可查看凭据名称、创建时间、最近使用和状态，并能安全撤销。

# 六、账号恢复

- [ ] **阻断项**：恢复流程不依赖安全问题或仅凭当前已劫持会话。
- [ ] **阻断项**：恢复码随机、哈希存储、限速、短时或离线保存，并在使用后失效。
- [ ] **阻断项**：恢复成功后重新评估旧凭据与现有会话，不能只添加新 passkey。
- [ ] **策略项**：高价值账号采用延迟、人工复核、职责分离或更强身份核验。
- [ ] **策略项**：恢复活动总会触发独立通知和可执行的争议/冻结入口。
- [ ] **策略项**：同步型 passkey 的 provider 账号恢复被纳入威胁模型。

# 七、会话、前端与隐私

- [ ] **阻断项**：WebAuthn 成功后创建新的服务端会话并防止会话固定。
- [ ] **阻断项**：Cookie 使用 Secure、HttpOnly 和适当 SameSite，敏感操作有 CSRF 防护。
- [ ] **阻断项**：前端存在 XSS 时不宣称 passkey 能保护已登录操作；同时执行 CSP 和输出编码。
- [ ] **策略项**：敏感操作根据风险要求近期 WebAuthn 再认证或 step-up。
- [ ] **策略项**：日志不保存私钥、生物样本、完整 assertion、完整 challenge 或无用途设备指纹。
- [ ] **策略项**：attestation、AAGUID、BE/BS 和使用历史有用途说明、访问控制和保留期限。

# 八、最小回归集

- [ ] type、challenge、origin、RP ID 任一错配均失败且状态不变。
- [ ] 同一响应第二次提交失败。
- [ ] credential ID 与账号、`userHandle` 任一归属错配均失败。
- [ ] UV 必需时，只有 UP 的响应失败。
- [ ] 签名、公钥或算法错配失败。
- [ ] 注册并发和 challenge 并发只能成功一次。
- [ ] 新增/删除凭据仅有旧会话、没有再认证时失败。
- [ ] 恢复后通知、撤销和会话处置均可观察。
- [ ] 零计数可按策略兼容，计数回退会产生风险事件。
