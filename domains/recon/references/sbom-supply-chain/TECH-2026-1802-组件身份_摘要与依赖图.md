# 定义

组件身份用于回答“它是什么”，内容摘要用于回答“具体是哪一组字节”，文档内引用用于回答“图中的哪个节点”，依赖关系用于回答“它与其他节点如何连接”。这些标识层次必须组合使用，不能互相替代。

## 边界

- 属于本技术：组件坐标规范化、摘要绑定、图节点引用、直接与传递依赖关系、标识冲突处理。
- 不属于本技术：签名者授权、构建平台可信度、漏洞是否可利用、许可证法律结论。
- 容易混淆：包坐标与下载地址、版本与摘要、文档局部 ID 与全局标识、依赖存在与依赖可达。

## 多层身份模型

### 1. 人类可读名称

名称便于显示，但容易重名、改名和大小写漂移。单独使用 `name + version` 通常不足以跨生态唯一定位。

### 2. 生态坐标

Package URL（purl）的基本结构为：

`pkg:type/namespace/name@version?qualifiers#subpath`

- `type` 与 `name` 必填；
- `namespace`、`version`、`qualifiers`、`subpath` 按场景可选；
- `qualifiers` 应只保留准确识别包所必需的信息；
- `subpath` 表示包根目录内的相对路径，不应拿文件名 qualifier 代替；
- purl 不包含 URL authority，即不承载用户名、密码、主机或端口。

purl 表达软件包坐标，不保证某个坐标在不同时间解析到相同字节，也不等同于可信下载源。

### 3. 内容摘要

摘要把声明绑定到具体字节。它适合：

- 校验传输或存储后内容是否变化；
- 把 SBOM、签名或来源证明绑定到目标制品；
- 区分同名同版本但内容不同的构建。

摘要不表达发布者身份、授权或安全性。相同源码和版本在非可复现构建中也可能产生不同摘要。

### 4. 文档内引用

CycloneDX 的 `bom-ref`、SPDX 的 `spdxId` 等引用用于连接本文件中的节点和关系。它们首先是图引用，不应在没有命名规则和作用域约定时当作全局身份。

### 5. 漏洞生态标识

CPE、漏洞库内部产品键和厂商公告名称常用于漏洞匹配，但与 purl 不一定一一对应。映射结果应保留来源、置信度和人工覆盖规则。

## 依赖图模型

一个可用于影响分析的 SBOM 至少需要：

- 明确的目标根节点；
- 唯一且可解析的组件节点引用；
- 从节点到依赖节点的有向关系；
- 直接依赖与传递依赖的可达性；
- 对未知、未解析或不完整关系的显式说明。

只有扁平组件清单时，可以回答“可能包含什么”，但很难可靠回答“目标为何受影响”“从哪个直接依赖引入”以及“删除哪个依赖会改变路径”。

## 标识与关系不变量

1. 每个文档内引用在其作用域中唯一。
2. 每条依赖边的起点和终点都能解析到现有节点。
3. 目标制品摘要与实际输入制品重新计算值一致。
4. 同一生态坐标若对应多个摘要，不静默合并。
5. 同一摘要若对应多个名称，保留别名和来源，不臆断它们属于不同字节对象。
6. 未声明版本的组件不自动补“最新版本”。
7. 关系未知与“明确没有依赖”是不同状态。

## 常见规范化风险

### 大小写与转义

不同生态对命名空间和名称大小写的规则不同。不能用一套全局小写规则处理所有 purl 类型。百分号编码和 qualifier 排序应遵循 purl 规范及对应类型定义。

### 版本别名

标签、语义版本、提交号、发行版修订号和容器标签表达不同层次。`latest` 或分支名不是不可变版本。

### 容器与平台差异

同一镜像标签可指向不同清单或平台制品。应在策略层绑定 OCI digest，并在需要时记录体系结构、操作系统和变体。

### 重打包与供应商补丁

发行版可能保留上游版本字符串但回移安全补丁。仅按上游版本匹配漏洞会产生误报；需要保留发行版、仓库和修订等限定信息，并结合供应商公告或 VEX。

### 跨格式转换

SPDX 和 CycloneDX 都能表达组件与关系，但对象模型和扩展能力不同。转换器应输出字段丢失报告，不能因目标格式可解析就宣称语义无损。

## 安全验证

使用虚构或公开样例进行以下检查：

1. 解析 purl，并按对应类型规则重新生成规范形式。
2. 重新计算制品摘要，与 SBOM 目标摘要比较。
3. 建立文档内引用集合，找出重复 ID、悬空边和不可达节点。
4. 对每个组件记录“原始标识 → 规范标识 → 漏洞库映射”，保留映射置信度。
5. 对同坐标不同摘要、同摘要不同坐标分别触发冲突而非自动合并。
6. 从目标根节点遍历依赖图，验证直接与传递路径可以解释。
7. 把未知关系单独统计，不把未知当空集合。

停止点：验证身份和图关系的一致性即可；无需连接或探测任何第三方运行系统。

## 检测与排查

- 同一个 `bom-ref` 或 `spdxId` 被不同组件复用。
- 依赖边指向不存在节点。
- purl 缺少必需类型或名称，或 qualifier 含空值和重复键。
- 同名同版本组件出现冲突摘要。
- 目标只有可变标签，没有摘要。
- 漏洞匹配系统把低置信度 CPE 映射当成确定命中。
- 组件存在于清单但从目标根节点不可达，且没有说明其作用。
- 转换前后节点数、边数或关键字段减少但没有损失报告。

## 常见误判

- “purl 相同，字节一定相同。”——错误；purl 是坐标，摘要才绑定字节。
- “摘要相同，所以来源可信。”——错误；摘要不包含身份或授权。
- “`bom-ref` 可以跨所有 SBOM 永久引用。”——错误；其作用域和生成规则必须另行约定。
- “组件列表包含传递依赖，就不需要关系图。”——错误；缺少路径会削弱影响解释。
- “CPE 与 purl 可无损自动互转。”——错误；两套标识模型和粒度不同。
- “没有版本就按最新版扫描。”——错误；这会制造没有证据的结论。

## 修复与回归

- 同时保留原始标识、规范标识和不可变摘要。
- 为文档内引用制定确定性生成规则，并处理碰撞。
- 在摄取阶段拒绝悬空边、重复引用和无效 purl。
- 对低置信度漏洞映射进入人工复核，不直接触发高风险结论。
- 每次格式转换比较节点、边、摘要、许可证和完整性字段。
- 回归数据至少覆盖重名包、无版本包、重打包组件、多平台镜像和循环/悬空关系。

## 标准映射

- purl：ECMA-427 / package-url specification
- SPDX 3.0.1：Core `Element`、`Relationship`，Software `Package`
- CycloneDX 1.7：`components`、`dependencies`、`compositions`
- CWE/CAPEC/MITRE ATT&CK：本技术属于供应链数据建模，不对应单一漏洞编号

## 核心要点

- 可泛化模式：**坐标用于定位，摘要用于绑定，局部引用用于连图，签名用于认证**。
- 容易误判的反例：相同名称、版本或 purl 并不自动代表相同字节。
- 检测信号：标识碰撞、悬空关系、可变标签、低置信度漏洞映射。
- 思考问题：为什么一个成熟 SBOM 同时需要 purl、摘要和文档内 ID？
- 常见误区：“只要有 SHA-256，就不再需要供应者和包坐标。”
