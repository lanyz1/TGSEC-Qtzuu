# SQL 注入公开学习路线

## 核心结论

SQL 注入不是“输入里出现了单引号”这么简单，而是应用把外部可控数据拼进 SQL 结构，使数据库把数据解释为语法。可靠修复必须恢复“命令结构与数据分离”，首选服务端参数化查询。

## 学习目标

完成本方向后，应能：

1. 用 `输入源 → 字符串构造 → SQL 执行点` 描述根因。
2. 区分可见结果、错误信号、布尔盲注、时间盲注、带外信号和二阶注入。
3. 判断数据库报错、输入过滤告警与真正 SQL 注入的区别。
4. 在源码中追踪用户输入到数据库执行 API 的数据流。
5. 选择参数化查询、标识符允许列表、最小权限和安全错误处理。
6. 为修复编写覆盖正常输入、边界输入和恶意形态的回归用例。
7. 只在公开在线实验室或本机隔离靶场进行最小验证。

## 分阶段练习

### 第一阶段：建立模型

- 能画出可控输入、查询构造和数据库执行三者关系。
- 能说明参数化为什么有效，以及转义为什么不应成为首选。
- 能解释“错误页被关闭”为什么不等于漏洞消失。

### 第二阶段：白盒识别

- 找到字符串拼接、格式化、模板化 SQL 和动态存储过程。
- 区分“值参数”与表名、列名、排序方向等“标识符/语法片段”。
- 检查 ORM 的原生查询、表达式拼接和绕过参数绑定的接口。

### 第三阶段：安全验证

- 只在靶场中验证响应差异、错误差异或稳定时序差异。
- 一旦能够证明输入改变了查询结构就停止，不读取无关数据、不扩大影响。
- 记录请求、预期、实际、停止点和修复建议。

### 第四阶段：修复与复测

- 把所有数据值改为驱动提供的参数绑定。
- 对无法绑定的标识符使用代码内固定映射，不接受任意字符串。
- 限制数据库账号权限，避免一个注入点扩大成全库或系统影响。
- 使用同一测试用例验证修复前失败、修复后阻断、正常功能不回归。

## 非目标

- 不整理真实目标利用记录。
- 不建立 payload、WAF 绕过或自动化数据提取字典。
- 不把“扫描器报高危”直接当作已验证漏洞。
- 不把输入过滤、统一错误页或 WAF 当作根因修复。

## 完成标准

- 能不依赖 payload 背诵，准确解释根因和安全边界。
- 能审查至少三种语言的数据库调用并识别错误拼接。
- 能为动态排序、动态列名和 `IN` 列表给出安全设计。
- 能区分参数化、预备语句、存储过程、输入验证和最小权限各自职责。
- 能产出带 `source_id`、标准映射、置信度和停止点的案例或技术卡片。
