# 白盒审计主线

代码审计不应从“搜索 SQL 关键字”结束，而应完成一条可解释的数据流：

```text
外部输入源 → 转换与存储 → SQL 构造 → 数据库执行点 → 数据库账号与结果出口
```

## 第一步：枚举执行点

优先找到：

- 数据库驱动的 `query`、`execute`、`exec`、`prepare`、`raw` 接口。
- ORM 的原生查询、literal、expression、动态过滤和排序接口。
- 存储过程中的动态执行语句。
- 报表、迁移、批处理和后台任务中的 SQL。
- 通用数据库封装层；不要只看控制器。

## 第二步：识别可控输入

输入不只来自 HTTP：

- URL、表单、JSON、GraphQL 变量、Cookie 和请求头。
- 消息队列、Webhook、文件导入和第三方 API。
- 数据库中先前保存的用户名、标签、备注和配置。
- 管理员输入；管理员身份不代表内容可以安全进入命令结构。
- 内部服务字段；跨服务边界仍需视为不可信。

## 第三步：追踪结构构造

重点检查：

- `+`、字符串插值、模板字符串、格式化函数。
- 为可选筛选条件逐段拼接 `WHERE`。
- 动态 `ORDER BY`、表名、列名、Schema 和操作符。
- 逗号拼接的 `IN` 列表。
- 把数组、对象或筛选 DSL 手工转换为 SQL。
- 先调用“转义函数”，再拼接进 SQL。
- 已调用 `prepare`，但输入早已被插入 SQL 模板。

## 第四步：确认执行语义

需要回答：

- 外部数据是作为独立参数传递，还是已经成为查询文本的一部分？
- 参数 API 是否只保护了部分字段，其他片段仍在拼接？
- 驱动是否允许多语句、客户端模拟预备或自定义类型转换？
- 动态标识符是否来自固定映射？
- 存储过程内部是否再次构造动态 SQL？
- 数据库账号具有什么权限？

# 常见语言审计线索

## Java / JDBC

高风险：

```java
String sql = "SELECT name FROM users WHERE id = " + requestId;
statement.executeQuery(sql);
```

安全边界：

```java
PreparedStatement stmt =
    connection.prepareStatement("SELECT name FROM users WHERE id = ?");
stmt.setLong(1, requestId);
```

还应检查 HQL/JPQL、MyBatis 字符串替换和 ORM 原生查询。

## Python / Psycopg

高风险：

```python
cur.execute(f"SELECT name FROM users WHERE id = {request_id}")
```

安全边界：

```python
cur.execute("SELECT name FROM users WHERE id = %s", (request_id,))
```

表名和列名不能作为普通值参数；Psycopg 应使用 `sql.Identifier` 等安全组合 API，或固定枚举映射。

## JavaScript / node-postgres

高风险：

```javascript
await client.query(`SELECT name FROM users WHERE id = ${requestId}`)
```

安全边界：

```javascript
await client.query(
  "SELECT name FROM users WHERE id = $1",
  [requestId],
)
```

同时审计模板字符串、查询构建器的 raw API 和 ORM 的 replacements/bind 配置。

## Go / database/sql

高风险：

```go
rows, err := db.Query(fmt.Sprintf(
    "SELECT name FROM users WHERE id = %s", requestID,
))
```

安全边界：

```go
rows, err := db.Query(
    "SELECT name FROM users WHERE id = ?", requestID,
)
```

实际占位符由驱动决定；PostgreSQL 驱动常使用 `$1`。

## PHP / PDO

仅调用 `prepare()` 不够。如果变量已经插入模板，查询仍不安全。

安全模式应把变量放在 `execute()` 参数或绑定接口中；占位符只能代表完整数据值，不能代表表名、列名或任意语法。

## .NET / ADO.NET

检查 `CommandText` 是否通过连接、插值或格式化构造。值应通过 `DbParameter`、`SqlParameter` 等参数对象传递，并尽量显式设置类型与长度。

# 安全验证流程

## 适用环境

- PortSwigger Web Security Academy 在线实验室。
- 本机仅监听回环地址的 WebGoat 或 Juice Shop。
- 自有或明确授权环境；本轮资料整理不对任何真实目标执行验证。

## 最小步骤

1. 记录正常请求与预期业务结果。
2. 选择不会读取、修改或删除无关数据的成对测试条件。
3. 比较响应内容、状态、错误或时序是否可重复受控。
4. 结合源码或数据库日志确认差异确由查询结构变化造成。
5. 证据足够即停止。
6. 修复后用相同用例复测，并验证合法输入仍正常。

## 证据字段

- 输入入口与参数名。
- SQL 构造文件、函数和执行 API。
- 数据流路径。
- 对照请求及重复次数。
- 实际差异。
- 数据库、驱动和关键配置。
- 数据库账号权限。
- 结论状态：已验证 / 代码推断 / 待环境验证。
- 停止点与未执行的高影响动作。

# 误区

- **错误页消失就是修好**：错误被隐藏后仍可能存在盲注。
- **ORM 自动安全**：raw/literal 和动态表达式仍可能拼接。
- **先转整数就永远安全**：类型转换可降低某个入口风险，但不能替代统一参数化策略，也不能解决动态标识符。
- **WAF 未告警就是安全**：WAF 是纵深防御，不证明代码结构正确。
- **扫描器高危就是已验证**：必须有可重复证据或白盒数据流。
- **内部数据可信**：二阶与跨服务路径经常由这一假设产生。
