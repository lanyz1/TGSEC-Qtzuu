# 盲注的本质

“盲”只表示应用没有直接回显数据库结果，并不表示数据库没有执行被改变的查询。测试者依靠间接信号判断条件真假。

## 布尔信号

可能的观察面包括：

- 响应正文中的元素是否存在。
- 状态码或跳转路径。
- 返回记录数量、分页信息或业务提示。
- 响应长度、结构化字段或模板分支。

可靠判定必须采用成对条件。只观察单个异常响应，无法排除会话状态、个性化内容、缓存和后端随机性。

## 时间信号

时间盲注把数据库条件转换成可测延迟。它最容易受环境噪声影响：

- 网络抖动与跨区域链路。
- 冷启动、连接池等待和数据库锁。
- 缓存命中差异。
- WAF、队列、重试和限流。
- 同一服务的其他高负载任务。

安全验证流程：

1. 先采集正常请求的延迟分布，而不是只记一次耗时。
2. 使用逻辑上相反的两个无害条件。
3. 交替发送对照，避免先后时段负载变化。
4. 重复少量次数，比较中位数与分布是否稳定分离。
5. 延迟取满足辨识的最小值，达到证据即停止。

只有隔离靶场或明确授权环境才允许做时间型验证。

## 带外信号

带外信号依赖数据库功能、运行权限和网络出口。它可能触发 DNS、HTTP 或其他外部交互，因此影响面更大。

本库只记录三个判断问题：

- 数据库是否具备产生外部交互的能力。
- 应用数据库账号是否拥有所需权限。
- 出口网络与监控是否允许并记录该交互。

不把真实回连域名、凭据或外传步骤写入学习资料。

# 二阶 SQL 注入

## 数据流

典型二阶链路：

```text
外部输入
  → 安全写入数据库
  → 另一个任务或后台功能读取
  → 拼接到新的 SQL 字符串
  → 数据库执行
```

第一次写入使用参数化，只能证明“写入点安全”，不能证明后续所有使用点安全。数据库中的历史数据、管理员录入内容和内部服务字段在进入新查询时都应重新视为不可信。

## 容易漏审的位置

- 报表、导出和批处理任务。
- 管理后台搜索与审核页面。
- 数据迁移、同步、ETL 和定时任务。
- 从数据库读取后拼入动态表名或排序字段。
- 审计日志、用户名、标签等被误认为“内部可信”的字段。
- 消息队列消费端和跨服务数据回流。

## 证据要求

二阶注入的报告必须同时指出：

- 初始输入和持久化位置。
- 后续读取路径。
- 不安全查询构造点。
- 触发后续查询的业务动作。

只看到数据库中保存了特殊字符，不足以证明二阶注入。

# DBMS 与驱动差异

差异会影响语法和观察信号，但不会改变根因。学习时应先识别驱动和数据库，再选择官方参数 API。

## PostgreSQL

- 服务端位置参数采用 `$1`、`$2` 等形式。
- `PREPARE` 创建的服务端对象只在当前会话内存在。
- Psycopg 和 node-postgres 都强调把查询文本与值分开传递。
- 值参数不能替代表名或列名；动态标识符需要驱动提供的安全组合 API或固定映射。

## MySQL 与 MariaDB

- 常见驱动使用 `?` 作为值占位符。
- 是否启用客户端模拟预备、多语句和字符集处理取决于驱动配置。
- 安全审计应检查实际驱动行为，而不是根据 SQL 文本外观推断。

## Microsoft SQL Server

- ADO.NET 的 SQL Server 提供程序通常使用 `@name` 命名参数。
- `sp_executesql` 可以安全绑定动态 SQL 中的值，但把输入拼进命令文本后再调用仍然不安全。
- 参数类型和长度应显式匹配业务字段，避免隐式转换带来性能或逻辑问题。

## Oracle

- 常见接口使用 `:name` 或位置绑定。
- 普通过程参数可以安全传值；过程内部若使用动态 SQL，仍需绑定变量。
- SQL 与 PL/SQL 上下文不同，审计时要确认实际执行接口。

## SQLite

- 虽然常作为本地嵌入式数据库，应用仍可能把外部输入拼进查询。
- 常见驱动支持问号或命名参数。
- “数据库不联网”只缩小影响面，不会消除注入本身。

## 语言与驱动占位符

- Go `database/sql` 的占位符由具体驱动决定。
- Psycopg 使用自己的参数标记规则，不能用 Python 字符串插值代替。
- node-postgres 使用 PostgreSQL 位置参数，标识符不支持普通值绑定。
- PHP PDO 支持命名或问号参数，但参数只能代表完整数据值。
- JDBC `PreparedStatement` 使用位置参数。

把一种语言或驱动的占位符机械复制到另一种环境，可能造成错误甚至回退到字符串拼接。

# 共同防护

无论 DBMS：

1. 使用驱动参数 API 绑定所有数据值。
2. 动态标识符采用固定业务枚举映射。
3. 避免存储过程内部动态字符串拼接。
4. 数据库账号按应用和功能最小授权。
5. 错误对外统一、对内可观测，但不要把隐藏错误当成修复。
6. 对持久化数据的每个后续 SQL 使用点重新建立信任边界。
