# 重点漏洞测试要点规范（编号化，供矩阵点对点应答）

本文件是漏洞挖掘「重点漏洞类型」的**编号化测试要点**权威来源。挖掘时对适用的漏洞类型**逐要点执行**，并在参数漏洞矩阵条目的 `checkpoint_response` 字段**点对点应答**。

**如何应答（`checkpoint_response`）**：

- 结构为对象：`KEY` = 测试要点编号（如 `SQL001`），`VALUE` = **是否符合的声明 + 为符合做了哪些操作**（如 `"符合。识别为 LIKE '%..%' 上下文，用 %' 闭合后构造"`）。
- **必填条件**：当该条目 `vuln_type` 在本规范中有对应要点（能归一到某前缀），且 `status ∈ {tested_not_found, doubtful, filtered}` 时**必填**；`found` / `not_applicable` 可空。
- `VALUE` 须与 `tests` / 报告证据一致，不得空泛套话；某要点在本场景确不适用时，也要在 `VALUE` 中声明「不适用及原因」，不要凭空省略造成漏答。
- 应答的 `KEY` 必须是该 `vuln_type` 对应前缀下的合法编号（见文末总表），门禁会校验 KEY 是否越界。

> **机读单一事实源**：编号→漏洞类型的映射固化在 `scripts/common.py` 的 `VULN_CHECKPOINTS`，门禁据此校验，不解析本 md。本文件供子代理/主代理阅读，两处由 code review 对齐；**新增或调整要点须同步改本文件与 `common.py`**。

## SQL — SQL 注入（generic）

| 编号   | 测试要点                                                                                                                                                                                                                                                                                                                          |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SQL001 | **必测防护规则**：以下每种类型至少测试3个不同的例子，检查其是否被过滤/拦截/替换/转义/放行，据实记入 `filter_probe`；<br /> - **空白字符和注释符**：如`空格`、`#`、`/**/`、`-- `等<br />- **SQL常用关键字**：如AND、OR、SELECT、WHERE等<br />- **SQL常用符号**：`‘`、`""`、`()`、`%`等 |
| SQL002 | **先判闭合再构造payload**：识别参数拼接上下文（`'...'` 字符串、`%...%` 的 LIKE、`(...)` 括号、数字型无引号、`ORDER BY` 等）针对性闭合，**严禁械套用固定 payload**                                                                                                                                             |
| SQL003 | **针对过滤规则定制payload**：至少尝试3种不同的绕过方式。关键字黑名单→大小写、内联注释、双写、等价函数/运算符等。探明空格被过滤/替换后→构造不带空格的payload 如使用无需空格的`&&`运算符代替AND、OR关键字或使用括号等。                                                                                                   |
| SQL004 | **充分尝试各注入类型**：联合查询、报错注入、布尔盲注、时间盲注逐一尝试；**无回显时必做盲注**，不因单一类型无回显即判无注入。                                                                                                                                                                                          |

## XSS — 跨站脚本（generic）

| 编号   | 测试要点                                                                                                                                                                                                          |
| ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| XSS001 | **黑名单绕过遍历**：遇标签/属性/事件黑名单时，遍历非黑名单标签（svg/video/audio/marquee/details 等）、事件（onerror/onload/ontoggle/onanimationstart 等）、协议与编码，**不因个别标签被拦即判安全**。 |
| XSS002 | **闭环验证输出上下文**：确认输入落到哪个页面哪个元素、是 `innerHTML` 还是 `textContent`、属性/JS/HTML 上下文；**存储型须到实际渲染页验证执行（跨 URL 也要验）**。                                 |

## CMDI — 命令注入（generic）

| 编号    | 测试要点                                                                                                                                     |
| ------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| CMDI001 | **探测分隔与拼接位**：在正常值中段注入 `;` `                                                                                         |
| CMDI002 | **无回显做带外/时延验证**：`ping -c` / `sleep` / `timeout` 制造时延，或 DNS/HTTP 带外；确无带外通道且无时延差异记 `doubtful`。 |
| CMDI003 | **遇过滤至少 3 种绕过**：命令替换、`${IFS}`/`<`/`%09` 替代空格、引号拼接打断、编码、变量拆分等。                                 |

## SSRF — 服务端请求伪造（generic）

| 编号    | 测试要点                                                                                                                                       |
| ------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| SSRF001 | **内网/本机/云元数据探测**：指向 `127.0.0.1`、内网段、`169.254.169.254`，对比时延·状态码·响应内容差异，判断服务端是否发起请求。    |
| SSRF002 | **协议与地址混淆绕过≥3 种**：`file://`/`gopher://`/`dict://` 协议、IP 进制/十进制/`@` 混淆、短域名、302 重定向、DNS rebinding。 |
| SSRF003 | **危害闭环**：读到内网/元数据内容或触发内网请求的证据；无带外与回显时以时延/报错差异佐证，确不可验记 `doubtful`。                      |

## PATH — 路径穿越 / 任意文件读（generic）

| 编号    | 测试要点                                                                                                                                      |
| ------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| PATH001 | **穿越序列与编码探测**：`../`、`..\`、`..%2f`、`..%252f`、`%2e%2e/` 等中段注入，记 `filter_probe`（是否过滤/规范化/截断）。 |
| PATH002 | **以已知文件坐实**：读到 `/etc/passwd`、`win.ini`、应用配置等越界文件内容或明确差异。                                               |
| PATH003 | **遇过滤至少 3 种绕过**：多重 URL 编码、点号变形、合法前缀+穿越、空字节/截断、绝对路径。                                                |

## UPLOAD — 文件上传（generic）

| 编号      | 测试要点                                                                                                                                                                       |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| UPLOAD001 | **后缀黑名单遍历**：按目标站点开发语言遍历所有可解析后缀（如 PHP：`php/php3/php4/php5/php7/pht/phtml/phar/phps`）+ 大小写/双扩展/`.` 截断/`%00`/多 MIME/魔术字节。 |
| UPLOAD002 | **路径穿越联动**：脚本上传成功但当前目录不解析时，尝试用路径穿越写到可解析目录，或改写解析规则文件（如 `.htaccess`）。                                                 |

## ENUM — 用户枚举（business_logic）

| 编号    | 测试要点                                                                                                                                                         |
| ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ENUM001 | **校验状态码一致性**：存在/不存在用户名的响应**状态码**是否一致（**不能只看 body**），应答时必须明确回复用户存在和不存在时的状态码分别是什么。 |
| ENUM002 | **校验响应头/时延一致性**：响应头、响应时间、跳转等是否泄露账号存在性（**不能只看 body**）。                                                         |

## AUTHZ — 越权/未授权访问（business_logic）

| 编号     | 测试要点                                                                                                                                                                                                               |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AUTHZ001 | **越权前正向确认会话角色**：测试前先用该会话成功访问"本角色专属且需登录"的页面/接口并拿到本人数据，确认会话确以目标角色在线；应答须回填用何请求确认、会话是否有效及其角色结果（防会话失效/未登录导致的假阴性）。 |
| AUTHZ002 | **完整跟踪跳转再判权限**：遇 3xx/302 严禁据状态码直接判"已拦截/无权限"，必须跟踪到跳转后的最终页面/响应体（落到登录页=拦截；落到目标数据=越权成立）；应答须回填 302 的 `Location` 与跟踪后的最终结论。         |
| AUTHZ003 | **以服务端数据差异坐实**：越权成立须以读到/改到他人或更高权限的真实数据为证，不能仅根据响应状态码不同、响应结果不同（有可能是不同的报错）判定漏洞存在。                                                          |

## RACE — 并发/竞态 TOCTOU（business_logic）

| 编号    | 测试要点                                                                                                                                                                                                                        |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| RACE001 | **识别 check-then-act 写操作**：库存/余额/限领/扣减/状态流转等「先查后写」的操作点。                                                                                                                                      |
| RACE002 | **构造未消费新包高并发发起**：不能重放已消费包；须**新造请求**并高并发（与 REPLAY001 联动），验超卖/超领/双花/越限。应答时必须回复未消费新包的关键特征（如sign）和在并发启动前{urlid}.log中没有grep到该特征的证据。 |
| RACE003 | **以服务端状态差异坐实**：库存/余额/领取记录的前后对比证据，而非仅「响应成功」。                                                                                                                                          |

## REPLAY — 重放（business_logic）
