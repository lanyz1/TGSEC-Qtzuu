# 第十技 · WAF 绕过 —— 和规则引擎玩"你画我猜"

> 猎手视角：WAF 是一台死读规则的机器——它认识"union select"这五个字母，却不认识你和它说的其实是同一件事。绕过 WAF 的本质，是找到"人能理解、规则读不懂"的表达方式。

**目标读者**：具备基础 Web 测试经验的安全工程师
**前置要求**：HTTP 协议细节（编码、分块、参数解析）、正则表达式阅读能力

---

## 何时启用本技

- 注入/上传/越权等攻击 payload 被拦截，响应出现 WAF 特征页（405 拦截页、关键词告警）
- 红队评估需要评估"纵深防御的第一层是否有效"
- **先想清楚**：绕过 WAF 是为了完成测试目标，不是为了炫技——如果业务验证不需要，别恋战

---

## 一、原理拆解

WAF 的判断链路与三个"翻译层"：

```
你的请求 → 网络层(分块/管线) → 解析层(编码还原/参数拼接) → 规则层(正则/语义)
```

绕过原理 = **三个层次不同步**：

1. **网络层**：WAF 读到的字节流 ≠ 后端读到的字节流（分块、管线）
2. **解析层**：WAF 解码一遍，后端再解码一遍（编码差异）
3. **规则层**：规则描述"这个样子"，但你写成"那个样子"（语法等价）

核心思想：WAF 与后端**必须做出完全一致的解析**才能防住你——任何一处分歧，都是你的空间。

## 二、五步猎洞法

### 第一步：识面 —— 确认 WAF 存在与身份

响应特征识别：

| 线索 | WAF |
|------|-----|
| 拦截页含 `aliyun`、`blockpage` | 阿里云 WAF |
| `Server: cloudflare`、`cf-ray` 头 | Cloudflare |
| 拦截页 `safedog` | 安全狗 |
| `X-Powered-By-360WZB` | 360 |
| 无明显特征 | 发探针试（如 `?id=1' union select`），观察拦截行为 |

同时确认拦截是**关键字级**（改一个字母就放行）还是**语义级**（怎么改都拦）——决定你走变形路线还是协议路线。

### 第二步：定点 —— 找"豁免清单"

WAF 通常有放行区，先测这些位置是否不检测：

```text
X-Forwarded-For / X-Real-IP 自定义头
JSON 报文体内部（部分 WAF 只检 URL）
XML/GraphQL 报文
PUT/PATCH 等冷门方法
文件名、Cookie 值
```

一个参数在 GET 里被拦、在 JSON body 里放行——这本身就是发现。

### 第三步：验证 —— 编码变形过规则

**规则层变形**（关键字级拦截适用）：

| 手法 | 示例（以 SQL 注入为例） |
|------|------------------------|
| 大小写混排 | `UnIoN SeLeCt` |
| 内联注释 | `UN/**/ION SEL/**/ECT`（MySQL） |
| 等价语法 | `or`→`\|\|`、`=`→`like`、空格→`%09`/`%0a` |
| 科学计数 | `1e0` 代替 `1` |
| 括号包裹 | `(SELECT(x)FROM(t))` 全程无空格 |
| 参数污染（HPP） | `?id=1&id=UNION&id=SELECT`——WAF 取第一个值，后端取最后一个 |

**编码层变形**（WAF 少解了一层）：

| 手法 | 说明 |
|------|------|
| URL 双重编码 | `%2527` → WAF 解一层是 `%27`（认为安全），后端再解成 `'` |
| Unicode/UTF-7 | 老场景 `+%AF%27%AD` 宽字符 |
| gzip/charset | `Content-Encoding: gzip` 报文体（WAF 不解压时裸奔） |

### 第四步：利用 —— 协议层技巧（编码救不了时）

```text
Transfer-Encoding: chunked        分块传输, 规则引擎看不全报文
  3
  ' o
  3
  r 1
  ...

Content-Length 错位               管线/请求走私的前置观察
超长填充                          前面塞 8KB 垃圾参数, 挤出 WAF 检测窗口
H2 伪头部/HPACK                  WAF 解析 HTTP/2 不完整的场景
```

### 第五步：收官 —— 记录有效手法，完成目标即回

记录"哪个位置、哪种变形"有效（这在报告里是纵深防御评估的核心内容），用变形后的 payload 完成原有测试目标（证明业务漏洞存在），**不**持续对 WAF 本身压测。

## 三、实战推演（虚构场景）

> 场景：授权测试虚构站点 `web.demo-example.com`，SQL 注入点已确认但 payload 被 WAF 拦截

1. **识面**：拦截页含云 WAF 特征，`?id=1'` 放行、`?id=1' union select` 拦截——关键字级
2. **定点**：GET 被拦；改 POST JSON `{"id":"1' union select"}` 也被拦（JSON 也有检测）；`X-Forwarded-For` 头注入放行——**头字段是盲区**，但注入口在 GET 参数，记下备用
3. **验证**：`UnIoN SeLeCt` 拦截；`UN/**/ION SEL/**/ECT` 放行且注入生效——内联注释生效，确认 WAF 不还原注释内容
4. **利用**：用注释变形完成数据验证（当前库名），原有测试目标达成
5. **收官**：报告两条：业务漏洞（SQL 注入高危）+ 纵深防御缺陷（WAF 未还原 MySQL 内联注释、头字段无检测）

## 四、对抗与绕过（按场景速选）

| 场景 | 首选手法 |
|------|----------|
| 关键字拦截 | 注释分割、大小写、等价语法 |
| 黑名单 payload 整段拦 | 编码（双重 URL/gzip）、分块 |
| 语义级检测 | 找检测盲区（头/JSON/PUT）、参数污染 |
| 拦截一切变形 | 评估绕过成本，转向其他入口（老接口、静态化页面源站） |
| 云 WAF（高防护档） | 优先找源站 IP（历史 DNS、证书透明日志、favicon hash 搜同源站）绕开入口 |

## 五、防御视角

1. 部署**语义分析** WAF 而非纯关键字规则
2. 确保解析一致性：后端与 WAF 的**编码/分块/参数取值策略对齐**（规则引擎取 first，后端取 last 是经典配置漏洞）
3. 隐藏源站：全站 CDN + 源站只白名单 CDN 回源 IP
4. WAF 是纵深不是修复：拦截率提升只给修复争取时间，**补丁永远打在业务代码**
5. 日志联动：WAF 拦截记录进 SIEM，同源高频变形触发自动封禁

---

## 六、踩坑记录

- 绕过手法"网上抄了没用"：**WAF 版本+云档位**决定行为，先做指纹再谈变形
- 花一小时绕 WAF，不如花十分钟找**未接入 WAF 的老接口**——覆盖不全比规则弱更常见
- 分块传输部分客户端库不发：手动用 `curl --header "Transfer-Encoding: chunked"` 构造
- `union select` 双写变 `uniunionon` 在部分 WAF 的"还原逻辑"下会被还原拦截——双写不是万能公式，测过才算数
- 别在报告里只写"绕过了 WAF"——**写清用的手法与 WAF 的失效原因**，不然安全运营没法修复

## 七、速查卡

```text
指纹:   拦截页特征 | Server头 | cf-ray
盲区:   自定义头 | JSON体 | PUT | Cookie
变形:   UN/**/ION | %2527双编码 | %09空格 | HPP
协议:   chunked分块 | gzip报文体 | 超长填充
终局:   找源站/找未覆盖的老接口
```
