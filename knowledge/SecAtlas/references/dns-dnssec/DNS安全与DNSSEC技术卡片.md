# 定义

DNS 解析安全是对 DNS 数据、查询传输、域名控制面和服务可用性的分层保护；DNSSEC 是其中用于验证已签名 DNS 数据来源与完整性的协议族，不等同于全部 DNS 安全。

## 边界

### 属于本技术的情况

- 递归解析器验证 `DNSKEY`、`DS`、`RRSIG`、`NSEC/NSEC3` 并形成信任链。
- 解析器通过随机事务 ID、随机源端口和 DNS Cookies 降低离路径伪造应答成功率。
- Stub 与递归解析器之间使用 DoT、DoH 或 DoQ 保护传输。
- 域名注册商、托管商和签名系统实施强认证、变更控制和委派巡检。
- 监控签名过期、父子 DS 不一致、信任锚轮换和异常解析行为。

### 不属于本技术的反例

- 把 HTTPS 证书有效直接当作 DNS 数据未被劫持的证明。
- 只开启 DoH 就宣称解析结果具备 DNSSEC 来源认证。
- 只给 zone 签名但没有把 DS 正确发布到父区，就宣称已建立完整信任链。
- 看到 `RRSIG` 就认定响应有效；签名必须由验证器沿信任链验证。
- 把所有 `SERVFAIL` 都判定为攻击；签名过期、时钟错误和委派配置错误也会导致验证失败。

### 容易混淆的相邻技术

- **DNSSEC 与 DoT/DoH/DoQ**：前者保护签名数据，后者保护特定传输段。
- **DNSSEC 与 TSIG/SIG(0)**：DNSSEC验证区数据；TSIG/SIG(0)用于特定 DNS 事务或消息认证，例如区传送和动态更新。
- **DNS Cookies 与 Web Cookie**：DNS Cookies 是 DNS 事务级轻量机制，不是浏览器会话状态。
- **保护性 DNS 与 DNSSEC**：保护性 DNS 执行威胁情报和策略阻断；DNSSEC验证数据来源与完整性。

## 成因模型

- **信任边界**：Stub 到递归解析器、递归解析器到权威服务器、子区到父区、域名所有者到注册商/托管商、签名服务到私钥存储。
- **可控输入**：DNS 查询与应答、缓存内容、区文件/动态更新、NS/DS 委派、托管平台 API、信任锚更新。
- **危险操作或 Sink**：把未经充分匹配或验证的应答写入缓存；将解析结果用于连接或安全决策；发布错误 DS/DNSKEY；接受未经审批的控制面变更。
- **缺失的安全控制**：来源认证、传输认证与加密、随机性、最小权限、MFA、变更审计、冗余、签名生命周期监控。

## DNSSEC 验证模型

### 数据对象

- DNSSEC 对 **RRset** 签名，不是对整条网络连接签名。
- `RRSIG` 保存 RRset 的签名及有效期等信息。
- `DNSKEY` 发布验证签名所需的公钥。
- 父区的 `DS` 引用子区 DNSKEY，使验证器可以从父区过渡到子区。
- `NSEC` / `NSEC3` 为名称或类型不存在提供可验证证明。

### 四种验证状态

- **Secure**：存在信任锚和完整信任链，相关签名均验证成功。
- **Insecure**：验证器能用已验证证据确认某委派没有 DS，因此后续分支未受 DNSSEC 保护；这不是签名失败。
- **Bogus**：安全委派表明数据应受保护，但签名缺失、过期、不受支持或内容验证失败。
- **Indeterminate**：没有足够信任锚判断该分支是否应受保护。

四种状态来自 RFC 4033。应用层若只看到一个笼统错误码，仍需结合验证器日志判断根因。

### AD 位的使用边界

`AD` 表示回答该请求的解析器认为相关数据已通过认证。只有当 Stub 同时信任递归解析器和到它的通信通道时，才能依赖这个信号；否则应使用受认证通道或在本地完成验证。

## 前置条件与变体

- **签名侧前置条件**：可靠的权威数据发布流程、受保护的私钥、正确时间、父区可发布 DS、可回滚的轮换流程。
- **验证侧前置条件**：启用验证、可信且可更新的根信任锚、正确时间、网络允许所需 DNS 报文和 TCP 回退。
- **常见变体**：单签名者、多签名者、托管商代管签名、KSK/ZSK 分离、组合签名密钥、NSEC 或 NSEC3。
- **平台差异**：托管 DNS 可能隐藏密钥与轮换细节；自建权威服务则由运营方承担算法、密钥、签名和发布全生命周期。
- **组合关系**：DNSSEC + 加密 DNS + 注册商强认证 + 保护性 DNS + 变更/签名监控，覆盖的威胁面比任一单项更完整。

## 典型风险模式

### 1. 离路径伪造与缓存投毒

攻击者试图抢在真实权威应答前提交可被解析器接受的伪造应答。事务 ID 和源端口的不可预测性扩大猜测空间，DNS Cookies 增加轻量校验，DNSSEC 则让验证器检查签名链。

边界：

- NAT 若压缩或重写端口，会削弱端口随机化。
- DNS Cookies 只对离路径攻击者提供有限保护。
- 未签名分支无法获得 DNSSEC 的数据认证能力。

### 2. 路径上观察与篡改

DoT、DoH、DoQ 可降低启用传输段上的窃听与主动篡改风险。它们不阻止解析服务提供方看到查询，也不自动验证权威数据的 DNSSEC 信任链。

### 3. 注册商或托管控制面接管

若攻击者能改 NS、DS 或区数据，单靠解析协议无法恢复正确的管理授权。特别是攻击者同时控制委派和签名材料时，可以生成密码学上有效的恶意解析结果。

根因控制是账号安全、强 MFA、最小权限、独立恢复渠道、域名锁、变更审批、关键记录巡检与告警。

### 4. DNSSEC 运营失败

常见故障包括：

- RRSIG 过期或尚未生效。
- DS 指向已移除或尚未发布的 DNSKEY。
- KSK/ZSK 或算法轮换顺序错误。
- 多权威节点数据不同步。
- 签名器或验证器时钟错误。
- 根信任锚未更新。
- 报文变大后路径不支持分片或 TCP 回退。

DNSSEC 的安全失败通常是“拒绝错误数据”，因此运营错误会直接转化为可用性事件。

## 安全验证

以下命令只读取公开 DNS 数据，不修改目标。命令存在与参数支持情况取决于本机工具版本。

```bash
# 请求 DNSSEC 相关记录；+dnssec 表示设置 DO 位，不等于本机已完成验证
dig +dnssec example.com A

# 查看父区 DS 与子区 DNSKEY/RRSIG
dig +dnssec example.com DS
dig +dnssec example.com DNSKEY

# 若安装 BIND delv，可使用本地信任锚执行验证
delv example.com A
```

观察要点：

1. `dig +dnssec` 只请求 DNSSEC 数据；是否可信取决于所用解析器、通道和本地验证方式。
2. 有 `RRSIG` 不代表签名已验证。
3. `AD` 只表示回答者声称已认证，不能跨不可信通道盲信。
4. 不要把示例域名的当前签名状态写成永久事实；DNS 数据会变化。
5. 达到“能区分记录、链条和验证结果”的学习目的后停止，不向第三方发起高频查询。

## 检测与排查

### 配置与代码审计线索

- 公开权威服务器是否同时开放递归。
- 解析器是否启用 DNSSEC 验证和自动信任锚更新。
- Stub 是否在不可信网络上盲信 AD 位。
- 是否仍按已过时的 RFC 8624 静态表选择算法，而未核对 IANA 当前注册表。
- 注册商/DNS 托管账号是否缺少抗钓鱼 MFA、变更审批或独立恢复渠道。
- DS、DNSKEY、RRSIG 的发布和轮换是否由可重复流程驱动。

### 请求与流量特征

- 验证失败率或 `SERVFAIL` 突增。
- 相同域名在验证和非验证解析器上结果明显不同。
- 权威节点之间的 SOA serial、DNSKEY、CDS/CDNSKEY 或关键 RRset 不一致。
- DNS 报文转为 TCP 的比例、截断标志和超时突然变化。
- 非批准的 DoH/DoT/DoQ 端点绕过组织解析策略。
- 高频、长标签、高熵子域等可能的 DNS 隧道信号；应结合端点进程和资产上下文，不能单凭字符串定罪。

### 日志与遥测

- 验证状态及失败原因，而不只是成功/失败。
- RRSIG 到期时间、签名任务状态和签名器时钟。
- 根信任锚版本和 RFC 5011 自动更新状态。
- 注册商、注册局、DNS 托管和区发布系统的管理员操作日志。
- NS、DS、A/AAAA、MX、CAA 等关键记录变更。
- 证书透明度日志中的未授权证书。

### 常见误报

- 未签名域返回 `Insecure`，被误报成签名遭篡改。
- 计划内轮换期间同时出现新旧密钥和签名，被误报成重复或异常。
- CDN、故障转移或 Anycast 造成多地址响应，被误报成劫持。
- QNAME 最小化、负缓存或策略解析导致查询路径变化，被误报成丢包。
- 保护性 DNS 的策略阻断被误报成权威域不存在。

## 修复与回归

### 根因修复

- 缓存投毒面：更新解析器，实现严格应答匹配、随机化、DNS Cookies，并对可验证数据启用 DNSSEC。
- 传输暴露：为明确的 Stub/递归或其他支持段部署经过认证的 DoT/DoH/DoQ。
- 控制面接管：收回账号、轮换凭据和签名材料，恢复正确 NS/DS/RRset，撤销未授权证书并审计历史变更。
- DNSSEC 配置错误：按父子区缓存时序修复 DS/DNSKEY/RRSIG，避免直接删除仍被缓存引用的密钥。

### 纵深防御

- 互联网权威与递归职责分离。
- 关键区使用独立运维权限、受保护密钥存储和双人变更。
- 启用自动化轮换但设置一致性检查、停止条件和回滚。
- 部署解析策略、威胁情报和端点/网络关联检测。
- 保留足以调查的日志，同时限制保留期和访问权限以降低隐私风险。

### 回归用例

1. 已签名正常记录在验证器上为 `Secure`。
2. 未签名委派被正确识别为 `Insecure`，不伪装成 `Secure`。
3. 实验室中的过期或错误签名被拒绝且日志能定位原因。
4. 新旧密钥轮换各阶段均保持可验证，父子数据符合设计状态。
5. 多权威节点的 SOA、DNSKEY、CDS/CDNSKEY 和关键 RRset 一致。
6. Stub 到递归的加密通道能认证预期解析器，不静默降级到未知服务。
7. 注册商/DNS 平台的未授权变更会产生告警并可从独立渠道恢复。

### 不完整修复反例

- 只切换到 DoH，不启用 DNSSEC 验证或控制批准解析器。
- 只开启 DNSSEC 签名，不发布 DS、不监控过期时间。
- 只依赖端口随机化，不升级存在已知缺陷的解析器。
- 为消除 `SERVFAIL` 永久关闭验证，而不修复错误签名或委派。
- 自动消费单个权威节点的 CDS/CDNSKEY，不检查其他节点一致性。

## 标准映射

- **CWE-345**：数据真实性验证不足；属于高层类别，具体漏洞映射时应优先选更精确 CWE。
- **CWE-350**：把反向 DNS 结果用于安全关键决策而缺少正反向验证。
- **CAPEC-142**：DNS Cache Poisoning。
- **CAPEC-598**：DNS Spoofing，偏路径上伪造场景。
- **MITRE ATT&CK T1071.004**：DNS 应用层协议滥用；属于检测相邻面，不是 DNSSEC 本身。
- **NIST SP 800-81r3**：权威 DNS、递归 DNS、加密 DNS、保护性 DNS和 DNSSEC 部署指导。
