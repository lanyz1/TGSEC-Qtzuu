# DNS 防守核查与被动验证清单

> 用途：公开资料学习、架构评审，以及对自有/获授权域名的低影响核查。默认只读取公开 DNS 数据，不做高频查询、伪造应答、缓存投毒、流量劫持或可用性测试。

## 0. 先确认范围

- [ ] 学习练习只使用 `example.com`、根区/IANA 官方资料或本地隔离实验室。
- [ ] 若核查真实域名，已确认域名属于自己或获得明确授权。
- [ ] 已记录允许查询的域名、解析器和时间窗口。
- [ ] 不向第三方权威服务发送批量、高频或构造型异常流量。
- [ ] 不保存查询中可能出现的内部名称、客户端 IP、账号或凭据。

## 1. 资产与角色

- [ ] 列出全部注册域名、注册商、注册局、DNS 托管商和账号所有者。
- [ ] 标出权威服务器、递归解析器、转发器、Stub 和签名服务各自职责。
- [ ] 互联网权威服务不向公众开放递归。
- [ ] 关键域至少有合理的权威冗余，且故障域、账号和变更路径不过度集中。
- [ ] 明确谁能修改 NS、DS、区记录、签名策略和信任锚。
- [ ] 记录关键 RRset：NS、SOA、DS、DNSKEY、A/AAAA、MX、CAA。

## 2. 域名控制面

- [ ] 注册商、注册局、DNS 托管和签名平台启用强 MFA；优先使用抗钓鱼认证器。
- [ ] 管理账号使用独立身份，不共享日常邮箱密码或恢复渠道。
- [ ] 权限按查看、改记录、改委派、改 DS、管理密钥拆分。
- [ ] 高风险变更需要审批或双人复核。
- [ ] NS、DS、MX、CAA 和关键地址记录变更会实时告警。
- [ ] 有独立于被保护域名的恢复联系渠道。
- [ ] 适用时启用注册商锁/注册局锁，并记录紧急解锁流程。
- [ ] 监控证书透明度日志，能识别和撤销未授权证书。

## 3. 权威 DNS

- [ ] 权威服务不承载不必要的软件和网络服务。
- [ ] 主区到从区传送经过认证并限制来源。
- [ ] 动态更新经过认证、最小授权和审计。
- [ ] 多权威节点 SOA serial 与关键 RRset 一致。
- [ ] TTL 与故障切换、缓存和变更风险相匹配，不为“快速生效”长期设置极端低值。
- [ ] 区发布有版本、审查、回滚和灾难恢复副本。
- [ ] 监控查询量、响应码、截断、TCP 回退、延迟和可用性。

## 4. DNSSEC 签名侧

- [ ] 明确签名由自建系统还是托管商负责。
- [ ] 私钥访问受限；关键区评估 HSM 或等效受保护密钥服务。
- [ ] 签名器使用可靠、受保护且冗余的时间源。
- [ ] 已确定算法时先查 IANA 当前注册表，不照抄旧 RFC 静态表。
- [ ] DNS 托管商、注册商/注册局和常见验证器都支持所选算法。
- [ ] RRSIG 有效期足以容纳发布延迟，又不会让失窃密钥长期有效。
- [ ] 监控 RRSIG 到期窗口，告警必须早于重签和人工处置所需时间。
- [ ] DS 正确发布到父区，且与当前 DNSKEY 对应。
- [ ] KSK/ZSK 或组合密钥轮换有时序图、停止条件和回滚方案。
- [ ] 算法轮换考虑双签期间报文变大、缓存和 TCP 回退。
- [ ] 多签名者/多提供商变更不会由单个节点单方面删除其他提供商记录。
- [ ] 自动消费 CDS/CDNSKEY 前检查所有权威地址的一致性；不一致时中止。

## 5. 递归与验证侧

- [ ] 只向获准的客户端提供递归，避免开放递归解析器。
- [ ] 启用 DNSSEC 验证，并保留 `Secure/Insecure/Bogus/Indeterminate` 或等价诊断。
- [ ] 使用 IANA/厂商提供的根信任锚，不从文档或网页手工抄写密钥。
- [ ] 启用并监控自动信任锚更新。
- [ ] 解析器事务 ID 和源端口不可预测，严格匹配请求与响应。
- [ ] 评估 NAT、防火墙或负载均衡是否压缩源端口随机空间。
- [ ] 软件支持时启用符合当前规范的 DNS Cookies。
- [ ] 支持 UDP 截断后的 TCP 回退，路径 MTU 和防火墙不破坏大响应。
- [ ] 启用 QNAME 最小化并观察兼容性，不将其误当成对递归解析器的隐私保护。
- [ ] 保护性 DNS 的阻断策略有来源、版本、例外、审计和误报处理。

## 6. Stub 与加密 DNS

- [ ] 明确哪些终端自行验证，哪些终端信任递归解析器验证。
- [ ] 依赖上游 AD 位时，终端同时信任该解析器和到它的通信通道。
- [ ] DoT/DoH/DoQ 客户端认证预期解析器，不只“看到加密就接受”。
- [ ] 禁止或管控未批准的外部加密 DNS，避免绕过组织策略和日志。
- [ ] 解析器日志的采集、保留期和访问权限符合隐私最小化。
- [ ] 网络检测已适配加密 DNS，不依赖旁路读取明文作为唯一信号。

## 7. 2026 根 KSK 轮换专项

截至 2026-07-20，IANA 公告 KSK-2024 计划于 2026-10-11 开始签署根区。

- [ ] 核对解析器厂商关于 2026 根 KSK 轮换的正式公告。
- [ ] 确认自动信任锚更新已启用且日志中没有长期失败。
- [ ] 确认软件包/设备固件处于厂商支持版本。
- [ ] 不把 key tag 或网页摘录手工写入生产配置；使用厂商或 IANA 的规范分发机制。
- [ ] 在轮换日前完成隔离验证和故障回退演练。
- [ ] 订阅 IANA `root-dnssec-announce` 等正式通知渠道。
- [ ] 轮换日监控验证失败、`SERVFAIL`、根 DNSKEY 和信任锚状态。

官方动态页：https://www.iana.org/dnssec/files

## 8. 无破坏性观察练习

### 8.1 查看普通与 DNSSEC 记录

```bash
dig example.com A
dig +dnssec example.com A
dig +dnssec example.com DNSKEY
dig +dnssec example.com DS
```

记录：

- 查询发给了哪个解析器。
- 响应是否带 `ad`、`do`、`RRSIG`；这些字段各自表达什么。
- `DS` 来自父区、`DNSKEY` 来自子区，二者如何关联。
- 当前没有某记录时，是 `NODATA`、`NXDOMAIN` 还是查询方法不对。

### 8.2 使用本地验证工具

若系统安装 BIND 的 `delv`：

```bash
delv example.com A
delv example.com DNSKEY
```

`delv` 的价值是执行验证，而不是只请求 DNSSEC 记录。若命令不存在，不为练习随意修改生产机器；在本地实验环境安装对应工具或只阅读输出示例。

### 8.3 查看根信任锚发布入口

只从 IANA 规范入口查看，不复制进配置：

- 说明页：https://www.iana.org/dnssec/files
- XML：https://data.iana.org/root-anchors/root-anchors.xml
- 规范：RFC 9718

### 8.4 停止点

满足以下条件即结束练习：

- 能区分“请求了 DNSSEC 数据”和“完成了 DNSSEC 验证”。
- 能解释 DS、DNSKEY、RRSIG 的关系。
- 能说明 AD 位为何需要可信解析器与通道。
- 能说明 DoH/DoT/DoQ 与 DNSSEC 解决的不是同一问题。

## 9. 验证失败排查顺序

1. **限定影响面**：单域、单解析器、单网络还是普遍故障。
2. **比较时间**：检查签名器和验证器时钟，但不先关闭验证。
3. **检查状态**：区分未签名 `Insecure` 与应签名却失败的 `Bogus`。
4. **检查链条**：父区 DS、子区 DNSKEY、目标 RRSIG 及其有效期。
5. **检查一致性**：逐个权威节点比较 SOA、DNSKEY、CDS/CDNSKEY 和目标 RRset。
6. **检查轮换阶段**：新旧密钥、签名和 DS 是否按计划共存或移除。
7. **检查传输**：截断、TCP 回退、MTU、防火墙和中间 DNS 代理。
8. **检查信任锚**：版本、自动更新和厂商已知问题。
9. **保留证据**：时间、解析器、原始响应、日志和变更记录。
10. **修根因后复测**：不要把永久关闭验证当作修复。

## 10. 通过标准

- [ ] 已签名区能由验证器稳定判定为 `Secure`。
- [ ] 故意构造的隔离实验室错误签名会被拒绝。
- [ ] 未签名委派被正确标记为 `Insecure`，不会伪造认证成功。
- [ ] 权威节点和父子委派持续一致。
- [ ] 信任锚和签名到期均有提前告警。
- [ ] 控制面未授权变更可被检测、阻断或快速恢复。
- [ ] 加密 DNS、DNSSEC 和保护性 DNS 的职责在架构文档中分开描述。
