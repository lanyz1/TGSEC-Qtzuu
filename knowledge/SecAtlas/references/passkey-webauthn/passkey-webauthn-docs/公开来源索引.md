# 收集边界

本索引只保留支撑依赖方安全设计、代码审计和低影响复测的规范、官方文档与实现参考，不保存第三方原文或媒体。

来源优先级如下：

1. 已发布的 W3C Recommendation 与 NIST Final Publication。
2. W3C Candidate Recommendation，用于跟踪 Level 3 新能力，但不得冒充已定稿 Recommendation。
3. FIDO Alliance 官方术语和部署说明。
4. OWASP Cheat Sheet 的实现者建议。

发生冲突时，以同一主题下状态更高、发布时间更新的规范性来源为准，并保留差异记录。

# 交叉核验与差异记录

1. 实时检索摘要曾把 WebAuthn Level 3 称为 W3C Recommendation；正式页面明确写的是 2026-05-26 Candidate Recommendation Snapshot。本库按正式页面记录，稳定实现基线仍以 Level 2 Recommendation 为主。
2. FIDO 将 passkey 概括为抗钓鱼凭据；严格说，抗钓鱼属性来自 WebAuthn 对 RP ID / origin 的验证者名称绑定。它不自动保护弱账号恢复、被接管的会话、站内 XSS、恶意浏览器扩展或已登录后的敏感操作。
3. 同步型 passkey 仍可提供抗钓鱼认证，并可在满足条件时用于 NIST AAL2；由于私钥可导出并进入同步体系，NIST 明确禁止将其用于 AAL3。设备绑定也不等于自动满足 AAL3，仍需非导出密钥、硬件保护、批准的密码技术和相应验证证据。
4. UP 只证明发生了用户在场/交互，UV 才表示认证器完成了本地用户验证。若业务把 passkey 当作多因素密码学认证器，服务端必须请求并验证 UV，不能只检查 UP。
5. `signCount` 下降或不递增只是克隆、故障或多设备行为的风险信号；规范不支持仅凭这一项断言密钥已被克隆。部分认证器的计数器可一直为零。
6. attestation 用于了解认证器来源和能力，不是所有消费级站点的注册前提。NIST 明确指出，面向公众的应用不应因缺少 attestation 阻断更安全的同步认证器；高保证企业场景可依据明确政策使用。
7. 生物特征或设备 PIN 在认证器本地完成验证。依赖方通常只接收 UV 等结果和签名证明，不应采集或宣称持有用户生物模板。
8. 账号恢复是另一条认证路径。若恢复或新增 passkey 只依赖已劫持会话、短信或弱客服问答，整体账号安全会降到该后备路径的强度。

# 引用与更新规则

- 稳定实现结论至少关联一个 W3C Recommendation 或 NIST Final 章节。
- Level 3 专属字段必须保留 `Candidate Recommendation` 状态，不写成既定跨平台保证。
- 不把 W3C 的 `MUST`、`SHOULD`、`MAY` 或 NIST 的 `SHALL`、`SHOULD` 混成同一强度。
- 不收录真实 credential ID、challenge、session、账号标识、生物数据、生产域名或设备管理信息。
- W3C Level 3 状态变化、NIST errata、FIDO 术语变化或 OWASP 页面大改时，重新核对并发布新数据版本，不覆盖旧版本。
