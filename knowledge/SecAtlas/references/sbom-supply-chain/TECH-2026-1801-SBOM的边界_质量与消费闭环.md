# 定义

SBOM 是针对某个软件对象的组件及供应链关系记录。它的直接能力是提高透明度；只有当内容足够准确、可定位、及时、可验证，并被采购、构建、部署和漏洞运营流程实际消费时，才会转化为安全收益。

## 边界

### 属于 SBOM 的内容

- 目标软件和组成组件的名称、版本、供应者与稳定标识符。
- 目标与组件之间、组件彼此之间的依赖关系。
- SBOM 作者、生成时间、生成工具和适用目标等文档元数据。
- 组件摘要、许可证、外部引用及覆盖完整性等扩展信息。
- 对未知、未覆盖或无法确认内容的显式说明。

### 不应由“有 SBOM”替代的能力

- 漏洞是否可利用：由漏洞分析和 VEX 等上下文信息补充。
- 构建过程是否可信：由来源证明、构建平台控制和验证策略回答。
- 制品是否被篡改：由摘要绑定和签名验证回答。
- 软件是否安全：仍需要安全开发、测试、代码审计、漏洞管理和运行时控制。
- 当前环境实际部署了什么：构建期 SBOM 与运行时资产清单可能不同。

### 相邻但不同的对象

- **SBOM**：组件库存与关系。
- **来源证明**：制品如何、从何处、由谁或哪个构建器产生。
- **签名**：对确定字节或声明提供完整性与认证证据。
- **VEX**：特定漏洞对特定产品的影响状态。
- **漏洞扫描报告**：某次扫描在特定规则和时间下的发现。

## 信任边界

基本链路为：

`软件生产者/生成工具 → SBOM → 分发渠道 → 消费者解析器 → 资产与漏洞系统 → 决策或阻断`

每个箭头都可能损失信息或引入错误：

- 生成工具看不到动态加载、运行时下载或厂商闭源组件。
- 同名组件、缺失版本或错误生态类型导致漏洞错误关联。
- 格式转换丢失关系、完整性或扩展字段。
- SBOM 与制品分离后，消费者无法确认清单对应哪个字节对象。
- 数据虽已入库，但没有告警、工单、部署门禁或更新流程消费。

## 质量模型

### 1. 对象绑定

必须能回答“这份 SBOM 描述哪个制品”。优先使用不可变制品摘要，并保留产品坐标和版本作为可读定位。只按文件名或 `latest` 标签关联会产生歧义。

### 2. 组件身份

组件记录至少要足以区分生态、命名空间、名称和版本。可使用 purl、CPE 或生态原生坐标，但不能假设不同标识体系天然一一对应。

### 3. 关系完整性

组件列表与依赖图不是同一件事。只有组件名称而没有直接/传递关系，会降低影响分析和路径解释能力。无法确认的关系应标为未知或不完整。

### 4. 内容准确性

声明的组件必须确实对应目标制品。锁文件提供“声明依赖”视角，最终二进制或镜像分析提供“实际打包”视角，运行环境又可能加入插件和下载内容。不同视角应标注生成上下文，不应静默合并成假精确结果。

### 5. 新鲜度

SBOM 应与制品版本共同发布和更新。时间戳只说明生成时间，不代表内容仍适用于后续重建、热补丁或运行时变更。

### 6. 可机读与互操作

使用固定版本的 SPDX、CycloneDX 等结构化格式，并执行对应 Schema 和语义校验。能被 JSON 解析不等于符合某个 SBOM 规范。

### 7. 完整性与认证

SBOM 应绑定目标摘要，并通过适合的签名或证明封装保护。即使签名有效，仍需单独检查签名者权限和 SBOM 内容质量。

### 8. 可行动性

接收方必须能把组件映射到资产、漏洞、负责人和处置流程。没有消费闭环的 SBOM 只是静态附件。

## 最低信息与成熟方向

NTIA 2021 正式基线把最小元素分为：

1. 数据字段；
2. 自动化支持；
3. 实践与流程。

其基础字段覆盖 SBOM 作者、时间戳、供应者、组件名称、版本、其他唯一标识和关系。

CISA 2025 草案提出把组件哈希、许可证、工具名称和生成上下文等纳入更新后的最低预期，并强化覆盖范围等要求。该文档截至 2026-07-20 仍为草案，因此适合用作内部成熟目标，不应写成已生效的最终最低要求。

## 安全验证

对一份公开示例或自有制品 SBOM，可执行以下低风险验证：

1. 固定声明的规范版本并运行官方或兼容 Schema 校验。
2. 检查目标对象是否具有不可变摘要，且与实际制品重新计算值一致。
3. 检查组件引用是否唯一，所有依赖边是否指向存在的节点。
4. 检查关键组件是否具有生态、名称和版本；不能确定时保留未知状态。
5. 对同一目标使用两种生成视角比对差异，并解释差异来源。
6. 检查生成工具、时间、上下文及覆盖范围是否存在。
7. 如果带签名或证明，按独立验证策略检查身份、颁发者、摘要和时间证据。
8. 用一个公开漏洞编号演练“组件定位 → 影响确认 → VEX/修复状态 → 负责人”的闭环，不对外部目标发起扫描。

停止点：证明结构、绑定、消费链路和已知缺口即可；不需要下载未知二进制或对第三方系统执行探测。

## 检测与排查

- **结构信号**：Schema 失败、未知规范版本、重复组件引用、悬空依赖边。
- **身份信号**：缺失生态或版本、purl 非规范化、同一坐标对应多个冲突摘要。
- **绑定信号**：SBOM 没有目标摘要、摘要算法过弱、摘要与制品不匹配。
- **时效信号**：制品已更新而 SBOM 未更新、生成时间晚于签名或发布流程的异常顺序。
- **覆盖信号**：只列直接依赖、未描述传递依赖、未声明未知项。
- **消费信号**：SBOM 已入库但没有资产匹配率、漏洞关联率、处置负责人或门禁结果。

## 常见误判

- “Schema 校验通过，所以组件一定完整。”——Schema 主要验证结构，不能证明现实世界覆盖率。
- “扫描器没有发现组件，所以组件不存在。”——可能是静态链接、压缩、重命名或分析能力缺口。
- “两个工具输出不同，必有一个错误。”——它们可能观察声明依赖、构建产物或运行环境的不同视角。
- “包含某漏洞组件，所以产品一定可利用。”——需要结合调用路径、配置、补丁和 VEX 状态。
- “SBOM 已签名，所以供应链可信。”——签名不验证构建过程，也不证明清单内容真实。

## 修复与回归

- 在构建流水线中为每个不可变制品生成并绑定 SBOM。
- 为未知和不完整信息保留显式状态，不用空字符串伪装确定值。
- 规范化组件标识，并保留原始标识以支持追溯。
- 对跨格式转换建立字段映射和损失报告。
- 把验证失败接入制品仓库或部署门禁，并为例外设置负责人和过期时间。
- 每次制品重建、依赖变化或安全修复后重新生成和发布 SBOM。
- 回归时同时检查结构有效性、摘要绑定、组件差异、关系完整性和消费结果。

- NIST SSDF：`PS.3.2`
- NTIA：The Minimum Elements for an SBOM（2021）
- SPDX：3.0.1 Core + Software Profiles；按需要增加 Security、Licensing 或 Build Profile
- CycloneDX：1.7
- CWE/CAPEC/MITRE ATT&CK：SBOM 是供应链透明度机制，不宜强行映射为单一漏洞或攻击技术

## 核心要点

- 可泛化模式：**库存声明 + 不可变对象绑定 + 来源/身份认证 + 验证策略 + 持续消费**。
- 容易误判的反例：结构有效、签名有效、组件命中漏洞都只是局部事实。
- 检测信号：悬空依赖、身份歧义、摘要不匹配、过期清单和没有处置闭环。
- 思考问题：如何区分“格式正确”“内容准确”“足以行动”？
- 常见误区：“只要生成 SBOM 就已经满足供应链安全。”
