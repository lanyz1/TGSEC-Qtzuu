# 定义

当应用使用外部可控输入构造 SQL 命令，而没有保持 SQL 结构与数据之间的边界时，输入可能被数据库解释成语法而不是普通值。这正是 `CWE-89` 描述的根因。

## 最小成因模型

SQL 注入成立通常需要同时出现：

1. **可控输入**：HTTP 参数、JSON 字段、Cookie、请求头、消息队列、文件内容、数据库旧数据或第三方接口数据。
2. **不安全构造**：字符串连接、插值、格式化、模板替换，或存储过程内动态 SQL。
3. **危险执行点**：数据库驱动、ORM 原生查询、存储过程动态执行接口等。
4. **结构可变**：输入最终能够改变 SQL 的语法树或执行意图。

其中第 4 点是判定关键。仅仅出现数据库报错、引号或 SQL 关键字，并不能单独证明注入。

## 数据与命令必须分离

不安全模式：

```text
sql = "SELECT name FROM users WHERE id = " + user_input
database.execute(sql)
```

安全模式：

```text
sql = "SELECT name FROM users WHERE id = ?"
database.execute(sql, [user_input])
```

第二种模式让驱动把查询结构与参数值分别传递。无论参数中有什么字符，它都应作为一个值处理，而不是重写命令结构。

## 参数化不等于某一种实现

“参数化查询”是安全边界；“预备语句”是常见实现方式。不同驱动可能采用客户端或服务端绑定，也可能缓存或不缓存执行计划。安全判断应关注：

- SQL 模板是否固定。
- 外部数据是否通过驱动参数 API 传递。
- 驱动是否把值与命令分离。
- 是否又在参数化之前或之后手工拼接了输入。

不能只根据函数名里出现 `prepare` 就判定安全。

## 参数通常只能代表值

参数占位符一般不能代表：

- 表名、列名、Schema 名。
- `ASC`、`DESC` 等排序关键字。
- SQL 操作符或任意表达式。
- 一整段 `WHERE`、`ORDER BY` 或 `IN` 语法。

这些动态结构应重新设计，或由代码把有限业务选项映射成固定 SQL 片段。把任意用户字符串“转义后”当成标识符仍然容易出错。

## 存储过程和 ORM 的边界

### 存储过程

存储过程只有在内部不拼接不可信输入，或内部动态 SQL 也正确绑定参数时才安全。把字符串传入 `EXEC`、`EXECUTE IMMEDIATE` 一类接口仍可能产生 SQL 注入。

### ORM

ORM 通常能安全绑定普通字段值，但以下接口仍需审计：

- 原生 SQL、raw query、literal/expression API。
- 手写排序、筛选或分页片段。
- HQL、JPQL 等查询语言的字符串拼接。
- 为性能优化而绕过 ORM 参数绑定的代码。

## 输入验证的职责

输入验证可以限制业务允许值、尽早拒绝异常数据并提供检测信号，但不能替代参数化。原因包括：

- 合法数据本身可能包含引号或关键字。
- 编码、字符集和数据库方言会改变转义含义。
- 数据可能先安全存储，后来在另一个查询中被不安全拼接。
- 过滤规则容易遗漏变体，并可能破坏正常业务。

对于无法绑定的排序方向或字段名，应使用严格枚举映射；这属于结构控制，不是通用关键字过滤。

## 影响由上下文共同决定

SQL 注入的实际影响取决于：

- 数据库账号具有哪些读写和管理权限。
- 当前语句是查询、更新、插入还是调用过程。
- 驱动是否允许多语句。
- 数据库是否暴露文件、网络或扩展能力。
- 应用是否把结果、错误、布尔差异或时间差返回给调用者。

因此风险评估不能只写“存在 SQL 注入”，还要说明可达数据、可执行操作、账号权限和已验证停止点。

## 不属于 SQL 注入的常见情况

- 输入导致类型转换失败，但始终作为绑定参数处理。
- 数据库返回语法错误，错误来源是服务端固定 SQL 自身缺陷。
- 用户能改变合法筛选值，却不能改变 SQL 结构；这可能是越权或业务逻辑问题。
- NoSQL、LDAP、XPath、OS 命令或模板语言被注入；它们属于相邻注入类别，不应误标为 SQL 注入。
- 扫描器仅根据状态码或错误关键词推测，尚无成对对照证据。

## 标准映射

- `CWE-89`：弱点根因。
- `CAPEC-66`：SQL 注入攻击模式。
- `WSTG-INPV-05`：Web 场景的测试目标与方法。
- 与认证绕过、越权、敏感数据暴露等影响可以同时存在，但这些是后果或组合问题，不替代根因分类。
